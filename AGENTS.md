# Repository collaboration ground

This repository holds self-contained design-process and research-system exemplars. Favor changes that make a visitor surface, source boundary, or collaboration decision more useful. Keep process proportional to the behavior being changed.

## Begin with current truth

- Confirm the current branch, worktree state, relevant issue or pull request, and nearest README before acting.
- Treat runnable source and artifacts as behavior authority. Use the nearest README for standing orientation, `planning/` for prospective terrain, `threadkeeping/` for settled rationale and re-entry, and GitHub for current work state.
- Treat `snapshot` as a recorded comparison input. Verify its equality with the named `main` revision, then create or update a living receiving branch from it; current behavior continues to come from runnable source on the accepted working branch.
- Preserve unrelated work already present in the worktree.
- When a prior record and current source differ, name the difference and continue from the current source.

- Start at `context-canvas-project-surface/context-canvas/README.md`, then read the target page and every CSS, JavaScript, iframe, and asset owner that materially shapes it.

- Use `context-canvas-project-surface/context-canvas/grammar-family.html` when Cloudflare delivery, contextual composition, coordinated rooms, durable undertakings, or visitor-owned surfaces enter the question.

## Write toward the desired state

- Use `supportive-change-writing` for substantial prose or instruction work. Its tone-goal index supplies the standing register, and its conditional context routes to the full Semantic Attractor Design source when polarity, prohibition, load-bearing negation, or recurring failure language shapes the result.
- Lead with the state the reader can create. Pair a load-bearing safety, privacy, or scope boundary with its affirmative replacement behavior.
- State what an evidence signal establishes before its scope boundary. Constitutive silence leaves an adjacent claim unspecified; route that claim to the observation that can establish it.
- Use a warm, direct, adult-to-adult register. Make evidence limits, decision authority, workload, and the next revisable move visible.

## Keep evidence useful

- Choose the smallest existing observation that answers the current question. A direct source reading often suffices; a visible layout change usually earns one affected-family browser comparison.
- Keep durable public or public-possible returns to the smallest decision-changing summary: the repository-defined check or sanitized command shape, normalized result, what it establishes, its coverage boundary, and the next decision when one exists. Raw output, logs, traces, browser state, credentials or headers, signed or query-bearing URLs, private routes or network coordinates, and user-specific paths remain local or with an existing access-controlled owner.
- Use one receiving surface. A public-safe pull-request body, workflow summary, task response, or Issue comment can complete the return; link it rather than creating a parallel receipt. A successor packet forms only for a materially new decision, authority need, or receiving job.
- GitHub Pages remains the standing hosted publication path. Its schema check, build, upload, and deployment remain one connected standard-runner job with GitHub-owned actions pinned to full commit SHAs. The budget-gated public-boundary receipt and advisory schema receiver-route receipt are the bounded automatic `main` intakes. The schema receipt keeps a pull request available for review while naming a route or contract that invites attention. The Core and Narrative unit receiver remains manually selectable and its matching pull-request trigger rests until `PROTOTYPE_UNIT_TESTS_AUTOMATIC=true`; the two LIMS/ELN proof paths retain explicit dispatch, variable, and confirmation boundaries. Dependabot scheduling remains dormant until a named receiver activates the included template. Local commands are the standing path for application and visual behavior.
- Add a script, validator, manifest, or recurring harness when repeated work demonstrates real turn savings or protects a consequential boundary.
- Give each review-ready pull request one receiving milestone and the smallest meaningful label set. Metadata supports navigation; the body remains the durable return for the result, related issues, change boundary, fitting evidence and its coverage boundary, recovery path, and next receiver.
- Close a collaboration cycle with the changed surface, the relevant observation, the current issue or pull request, and one clear re-entry move.

## Keep attribution legible and proportional

- Read [`AUTHORS`](AUTHORS) for copyright-holder identity,
  [`GOVERNANCE.md`](GOVERNANCE.md#how-to-attribute-contributions) for the
  contribution and publication pattern, and [`attribution.yml`](attribution.yml)
  for their bounded machine-readable projection.
- Use [`CITATION.cff`](CITATION.cff) when a person or tool asks how to cite the
  repository. Use truthful Git author metadata, agreed `Co-authored-by`
  trailers, and reviewed pull requests for contribution credit.
- Treat an independently renderable public HTML document's `<head>` as its
  file header. Current visitor carriers and their canonical generator
  templates carry the human author in metadata and the approved attribution
  in visible content.
- Let Git author metadata, agreed `Co-authored-by` trailers, and reviewed pull
  requests credit the people who made a change. Keep commit prose focused on
  the change.
- Keep ordinary scripts, stylesheets, tests, schemas, manifests, and source
  comments focused on their behavior. The centralized carriers above hold
  standing personal-name attribution. A source comment earns its place when a
  material provenance or generation boundary changes how the file should be
  edited.
- Preserve upstream notices in forks and adaptations, then add truthful
  adaptation credit where appropriate. Write resolved publication identity
  directly into source and generated visitor artifacts.
- Use `attribution.yml` as the bounded machine-readable projection and
  validation input. `AUTHORS`, `LICENSE`, `GOVERNANCE.md`, `CITATION.cff`, Git
  history, and copy-local notices retain their named authority and carrier
  roles.
