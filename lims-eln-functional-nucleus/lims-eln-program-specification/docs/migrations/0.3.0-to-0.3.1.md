# Migration guide: 0.3.0 to 0.3.1

Release `0.3.1` strengthens the control plane while preserving the domain
requirements and canonical simulated closure from `0.3.0`.

## Consumer actions

1. Update specification bindings from `spec-v0.3.0` to `spec-v0.3.1`.
2. Resolve governance through the canonical `governance-v2.0.1` tag recorded
   in `constellation.lock.json`.
3. Treat `receipts/promotion-receipt.json` as the release-state evidence
   record. Candidate state carries zero provenance and a null release
   coordinate. Released state carries observed provenance, check contexts,
   ruleset evidence, and CODEOWNER evidence.
4. Configure protected branches with deletion and non-fast-forward protection,
   one approval, CODEOWNER review, last-push approval, and review-thread
   resolution. Record an empty hosted-context list for the current `$0` resting
   state; a separately reviewed activation can add `program-validation` when a
   funded execution path is available.
5. Run `scripts/validate_pinned_sources.py` with all sibling repository roots
   during settlement. The command accepts a candidate only when
   `--allow-pending` is explicit.
6. Run the language, program, secret-shape, and unit-test checks before
   promotion.
7. Bind consumers to `DATA-CONTRACT-001` and
   `DATABASE-MIGRATION-CONTRACT-001`. Implementations satisfy its tool-neutral
   capability requirements through the selected Flyway Community 13.0.0
   profile and publish an immutable migration head, executable artifact digest,
   validate/info evidence, retained-test results, and catalog digest before
   settling the database release manifest.
8. Treat the eight records in `receipts/database-open-receipts.json` as
   future-observed obligations. Close them with configured-environment,
   representative-rehearsal, recovery, security, and accountable acceptance
   evidence at the implementation release coordinate.

## Compatibility

The bounded-caller operation identifiers, proof classes, open observed
receipts, and canonical selected-future closure identity remain stable.
Release metadata, validation strictness, and automation contexts advance in
this patch. The carried canonical closure retains its immutable governance
2.0.0 record identity; governance 2.0.1 validates that historical payload while
governing the current program surfaces.

The additive database contracts use version `1.0.0` and carry their own stable
identities. They enrich release `0.3.1` while preserving the existing bounded
caller identifiers, canonical closure, and nine original open receipts.

The selected Flyway profile replaces migration ordering, history, checksum,
coordination, and status behavior previously projected onto custom orchestration.
Existing end-to-end domain tests and parameterized clean, predecessor, failure,
replay, and convergence scenarios remain the transition oracle. Vendor upgrades,
cross-vendor data movement, semantic reconciliation, restore, and accountable
acceptance retain their distinct program boundaries.
