# Core iframe route stability settlement

## Desired state

The current Core Architectures pack can travel as a finite iframe population
without changing authored prototype identity or turning packaging into public
activation. One tracked contract names the pack hub and 21 current prototypes,
plus one supplemental Context Canvas instrument. It records exact versioned
aliases, source owners and standings, reader jobs, and present activation
standing without recasting the supplemental instrument as a Core Architecture.

The first route family is `https://iframes.vik.guru/v1/core/`. Its version token
names a stable public grammar rather than a Cloudflare implementation detail.
Paths outside the 23 declared aliases remain unmatched by this package.

## Package contract

- `public-iframe-route-manifest-v1.json` is the delivery projection contract;
  the existing Core pack manifest remains the current source-identity index.
- The dependency-free packager validates one hub and 21 one-to-one prototype
  records before reading any artifact into the projection. It separately
  validates the one supplemental Context Canvas source owner.
- Each prototype is emitted byte-for-byte as its route-local `index.html`.
  Only the hub receives projection-local sibling and manifest links. The
  supplemental Conditioning Field receives a deterministic, single-file
  embedded projection with its shared shell and popup exits omitted.
- `manifest.json` preserves the authored source manifest. The generated
  `route-manifest.json` records deterministic source and projection digests,
  static-resource observations, navigation observations, and activation
  standing.
- Optional package-local media is explicit per route. Each entry binds one
  regular source file to a bounded route-local target and content type. Inline
  media remains available; statically observable ambient references and path
  escape do not.
- The ignored output is replaceable build material. Failed validation leaves
  authored files unchanged, and the persistent builder stages a complete
  generation before replacing its prior tool-owned directory.

The resting Strategy Canvas v0.1.1 compatibility alias is not part of the 23
primary routes and is not generated. Nested Strategy build inputs and other
repository HTML remain outside this population.

## Static resources, navigation, and activation

Static runtime-resource references and user-activated navigation are different
observations. The packager follows resource-bearing markup plus reachable CSS,
SVG, and HTML package files, and rejects selected JavaScript network
primitives. It does not claim that source inspection proves every dynamic
browser request. Request-graph and delivery-policy evidence remain activation
requirements.

External source citations remain available. Three current local links do not
resolve inside the exact route package and remain visible in its receipt:

- PODA points to its Context Canvas reading companion;
- Strategy Canvas points to its adjacent published JSON Schema; and
- the Core Architecture Family Index points to its Context Canvas orientation
  index.

The package does not silently rewrite those links. Their parity and recovery
choices stay with the adapted-receiver issue. A route marked `eligible` must
have no unresolved local navigation; other activation standings preserve their
named review gate. Upload, destination configuration, signed-out observation,
and activation remain independently reviewable work.

## Evidence boundary

The focused unit suite proves manifest agreement, pinned alias identity, path
portability and symbolic-link safety, explicit static package-resource graphs,
source preservation, deterministic output, hub navigation, and the exact
output allowlist. The real check forms 23 route entries across 26 files in a
temporary directory. The persistent build writes the same package beneath
`.iframe-route-build/`.

This evidence does not establish dynamic-request absence, live Cloudflare
routing, caching, response headers, iframe sandbox policy, signed-out
availability, or a route's reader and disclosure fitness. It creates the finite
artifact that those later checks can receive.

## Receiver sequence

1. Review the route contract and package as the current Issue #71 front.
2. After acceptance, let the public-reference materializer consume the exact
   route and carrier contract, beginning with one eligible route.
3. Run adapted-receiver observation alongside that materializer work.
4. Activate routes individually only when each closure, carrier, disclosure,
   fallback, upload, and signed-out entry receipt is present.

Spark becomes useful when the route-package pull request has a pinned head SHA.
Its bounded job is observation across the four adapted root/Context receivers:
layout, reduced motion, JavaScript and no-JavaScript behavior, keyboard and text
equivalence, state recovery, navigation, and request graphs. It returns one
evidence row per receiver and makes no repository edit, route, upload,
materialization, or publication decision.
