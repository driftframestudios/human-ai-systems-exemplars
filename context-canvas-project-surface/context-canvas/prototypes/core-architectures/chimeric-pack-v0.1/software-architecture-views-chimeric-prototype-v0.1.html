Software Architecture Views

Feature Instantiation / Dependency Shape Map

A view-based architecture artifact that maps what a modeled feature or system element touches when instantiated: modules, runtime components, data stores, interfaces, deployment surfaces, tests, ownership, governance, and rationale.

Family · Shared Surfaces and Topology Placement · Implementation / Recovery Shape · View-based attachment map v0.1 · HTML + SVG + JSON-LD

Quick Use

Use this when

A feature, workflow element, AI behavior, service transition, or implementation change looks local, but the team needs to see what it touches across architecture views.

This restores

Feature-to-system attachment visibility.

Good next question

If we pull this feature into view, what does it bring with it?

Modeled Element

Start with one modeled element. The views expose its attachments from different architectural perspectives. Order and visibility are focus state; stable IDs remain semantic identity.

Selected View Set

Choose the smallest useful view set. Hiding a view supports focus; it does not delete its attachments or remove them from JSON / JSON-LD exports.

Semantic Locality

      

        

          Preferred phrasing
          
    
            
  • Which modeled element are we pulling into view?
    • 
            
  • Which views expose the attachments we need to understand?
    • 
            
  • What does this feature touch when instantiated?
    • 
            
  • Which attachment should become a scenario, test, topology revision, or upstream update?
    • 
          

        

        

          Replacement-state guidance
          
    
            
  • Instead of “This is just a small feature,” use “This feature may have a small visible surface and a larger attachment shape.”
    • 
            
  • Instead of “The code is risky,” use “The attachment map can show which modules, runtime components, data stores, interfaces, and tests carry the risk.”
    • 
            
  • Instead of “This broke,” use “The implementation evidence is showing which attachment needs revision or protection.”

Recovery Calibration

      

        
Strain cues
A small feature request repeatedly expands; people feel risk but cannot localize it; data, audit, permissions, or ownership appear late; runtime behavior differs from module expectations.

        
Stabilizing read
The collaboration needs feature-to-system attachment visibility.

        
Named geometries
Attachment Obscurity · Testless Unease · Service-Layer Invisibility · Upstream Revision Hesitancy.

      

    


    

      
Source Note

      
Source lineage: Documenting Software Architectures: Views and Beyond by Paul Clements, Felix Bachmann, Len Bass, David Garlan, James Ivers, Reed Little, Paulo Merson, Robert Nord, and Judith Stafford. Local adaptation: feature-centered instantiation and attachment mapping. The artifact chooses the smallest useful view set needed to understand what a modeled element touches.

view, viewpoint, viewtype, stakeholder concerns, module, component-and-connector, allocation, behavior, software interface, rationale, architecture description.

        
Local language
modeled element, feature instantiation path, attachment, dependency shape, selected view set, attachment confidence, evidence route.
