# Technology Fit Sampling Tableau — Prototype Addendum v0.1

## Purpose

The **Technology Fit Sampling Tableau** is a technology-decision profile of the Narrative Sampling Tableau.

It applies verbalized sampling, expectation, focalization, opportunity formation, indeterminacy, and Core Architecture routing to a front-end stack decision. Its primary purpose is to lower the interaction cost of asking a well-formed multiplicity question while keeping framework popularity, contextual fit, evidence, and long-term optionality distinct.

## Central determination

Two probability objects are required.

```yaml
default_likelihood:
  probability_of_what:
    "P(generic-LLM-first-recommendation | prompt condition)"
  semantics:
    "Open-exclusive distribution. Listed values plus tail mass sum to one."
  use:
    "Make statistical popularity and prompt sensitivity visible."
  status:
    "Model-verbalized distribution until measured through repeated sampling."

six_month_fit:
  probability_of_what:
    "P(six-month-fit-without-structural-rewrite | declared outcome and evidence)"
  semantics:
    "Independent candidate events. Values may overlap and need not sum to one."
  use:
    "Support a contextual planning decision."
  status:
    "Planning estimate until linked to observed spike or pilot outcomes."
```

This separation operationalizes the Field Guide distinction between **popular default** and **fit-for-purpose option**.

## Technology gaps and methodological gaps

The prototype uses one `GapRecord` base with five classes:

- `methodological`
- `technical`
- `organizational`
- `evidence`
- `boundary`

Technical gaps are first-class. Framework choice depends on concrete behavior involving native semantics, accessibility verification, SVG transforms and label density, JavaScript resource lifetimes, framework-version assumptions, static or server deployment, dependency aging, and layer replacement.

Methodological gaps remain first-class for candidate coverage, prompt sensitivity, calibration, commensurability, and the boundary between planning fit and formal statistical fit.

## Stack composition

A front-end stack is represented as a set of independently reviewable layers:

```yaml
stack_layers:
  - "rendering and component model"
  - "styling and cascade"
  - "component primitives"
  - "state and data"
  - "build and deployment"
  - "testing and verification"
```

The palette can create a new composed candidate without collapsing framework, styling, primitive, state, build, and test decisions into one monolithic label.

## Decision posture

The seed decision selects **React + CSS Modules + headless accessible primitives** and **Svelte + component-scoped CSS** for equal low-fidelity spikes.

This is a learning decision rather than a durable stack mandate.

The two candidates preserve materially different framework commitments while remaining plausible for the same static, accessible, SVG-rich collaboration surface. A platform-first Web Components candidate stays held as a next-round option if swapability or operational-calm questions remain active.

## Low-fidelity comparison contract

Every selected candidate receives the same fixtures:

1. semantic form and status feedback;
2. dense SVG coordinate and label-placement surface;
3. responsive comparison and inspector;
4. editable state with JSON / JSON-LD round trip;
5. styling or component-layer replacement.

The surface records `planned`, `working_example`, `in_progress`, `observed`, `verified`, `blocked`, or `deferred`. The sample state uses planning and working-example states rather than claiming completed verification.

Current exports use `uncalibrated_verbalized_sample`, `uncalibrated_planning_estimate`, `sample_state`, and `working_example`. Browser imports normalize the earlier `illustrative_verbalized_sample`, `illustrative_planning_estimate`, `illustrative_seed`, and `illustrative_walkthrough` values before validation and rendering, so a prior local save remains usable without carrying the older vocabulary into a new export.

## Formal statistical fit boundary

Weighted dimensional fit, verbalized probability, and planning probability remain separate.

A formal statistical-fit record becomes appropriate when the collaboration has:

- an observed outcome variable;
- a unit of analysis;
- repeated observations or a sampling frame;
- a named model or test;
- assumptions and diagnostics;
- an uncertainty interpretation;
- a replication or out-of-sample plan where relevant.

Until then, `formalStatisticalFitBoundary.status` remains `not_yet_applicable`.

## AI Prompt Capsule

The self-contained prototype implements `prompt-capsule/0.1.0` without changing
the Technology Fit state or schema version. Its plain view is complete on its
own. The skill-assisted view adds exact public source coordinates for
Practitioner Probe, Evidence-Grounded Research Spike, and Stateful Artifact
Behavior Contracts. Both views include the visitor-surface-change and
repository-reentry loops with a condition that explains when each loop fits.
A native Related loops disclosure exposes the same two links and remains
usable in the no-JavaScript reading.

The capsule carries:

- materially distinct candidates;
- composable stack layers;
- both probability objects;
- intervals and estimate status;
- dimensional fit;
- evidence that would move estimates;
- methodological and technical gaps;
- equal-spike suggestions;
- Practitioner Probe and Core Architecture routes;
- decision, abstention, and review conditions.

One canonical fingerprint represents the material sampling state in both
views; selector choice and transient visitor state do not change it. The
source-authored plain Markdown remains readable without JavaScript. Native
radio controls select a view, an accessible status reports selection and
exchange results, and copy and download return the active Markdown exactly.
The frozen programmatic seam exposes detached state and read-only projection
methods without a state mutator.

A structured AI response can enter the prototype as a successor run. Human
edits, AI-proposed values, and observed evidence remain distinguishable through
state and provenance fields. Collaborator prose is escaped where it enters the
GitHub Flavored Markdown document. Stable values inside code spans retain their
literal identity, including underscores, ampersands, and backticks.
