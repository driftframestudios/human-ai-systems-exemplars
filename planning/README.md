# Planning surfaces

This directory holds prospective, returnable collaboration surfaces outside the repository's execution and publication paths. It is a place to explore consequential choices, compose design sprints, preserve unasked questions, and prepare work that may later become code, a visual contract, an architecture decision, or a settled route in a section README.

Planning is deliberately distinct from `threadkeeping/`:

| Surface | What it carries | What it does not claim |
| --- | --- | --- |
| `planning/` | Options, dependencies, design-sprint terrain, open questions, research, evidence-based capability assessment, and Now / Next / Later continuations | Runtime truth, deployment authority, or a readiness certification |
| `threadkeeping/` | Decisions, rationale, assumptions, source boundaries, review history, and re-entry position | A transcript, a project-management gate, or visitor content |
| GitHub Issues | Bounded work with a named outcome, acceptance evidence, ownership, discussion, and a useful path to a branch or pull request | The complete design terrain, architectural rationale, or a duplicate roadmap |
| GitHub Projects | Optional views across issues and pull requests when filtering, sequencing, or shared triage becomes useful | A second planning corpus or a requirement for every collaboration |
| Visitor and prototype source | The experience another collaborator or visitor can actually inspect and use | Collaboration history or why a prior pass happened |
| Architecture decisions | Stable, consequential choices once their receiving context is known | Every provisional idea considered during planning |
| Pull requests | The exact proposed source change, review conversation, verification evidence, and merge result | Long-horizon planning or the only record of why a durable choice was made |
| CI and release receipts | Reproducible evidence about a specific revision | The rationale for the architecture or the human meaning of a choice |

The planning surface references source material instead of becoming a second copy of it. When a concept settles, the receiving package or section README becomes the concise route to it. When rationale or re-entry context matters, `threadkeeping/` keeps that line alive.

## Working posture

Planning surfaces use a small continual-writing rhythm:

1. **Hydrate** — name the actual request, relevant authorities, constraints, and what should remain open.
2. **Explore** — produce options, maps, probes, and relationships without implying a gate.
3. **Rest** — read existing code, research, reviews, and real use back into the plan.
4. **Settle** — test necessity, smallest useful form, dependencies, and constitutive silences.
5. **Hand forward** — name the next useful move and link the receiving artifact.

An individual planning file may be long. Its directory README stays compact and routes future collaborators to the material that currently matters.

## Collaboration rules

- Preserve the repository's current top-level structure unless a receiving implementation materially benefits from a narrower change.
- Keep HTML, CSS, and SVG as the Context Canvas runtime substrate. Build-time verification and distribution tools do not become visitor dependencies.
- Treat `main` as the broadest cross-platform hydration surface because some collaborators can read only that branch. Use branches when they improve review, isolation, or recovery; do not turn branch choice into a judgment about the work.
- Give each active item one operational owner. A planning row may point to an Issue; the Issue owns its immediate state; a pull request owns the proposed diff; Git and deployment own what landed. Mirror links and consequences, not competing status fields.
- Keep planning and threadkeeping outside public deployment by default.
- Prefer links and typed relationships to duplicated content.
- Record what is settled, what remains open, and what another collaborator can do next.
- Keep open questions visible. They are collaboration handles, not evidence that the plan failed.
- Normalize contracts and mechanics while preserving the Context Canvas's plural visual expression.
- Reuse the established harness, manifests, and small root development toolset when a reproduced visitor-facing need calls for them. New checks and tools earn a place by making a specific visitor condition observable; compliance structures, readiness scores, and abstract authority layers remain outside this planning surface.
- When current tools cannot observe a reproduced need, describe the need first and let the smallest useful check form with the repair. A named human collaborator decides whether that observation stays local or earns a place in the shared harness.
