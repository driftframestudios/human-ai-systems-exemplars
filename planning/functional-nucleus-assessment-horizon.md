# LIMS/ELN functional nucleus — assessment and horizon

**Assessment date:** 22 August 2026

**Scope:** six repositories, their present affordances, and the next functionality-bearing choices

The functional nucleus is coherent and useful now. It carries one problem through intent, executable contracts, an actual Python implementation, a selected-future simulation, comparative evidence, reusable governance, and a human-facing design surface. Its strongest principal-level quality is separation of authority: specification, execution, forecast, comparison, governance, and human interpretation each have a named home and exchange versioned artifacts.

The maturity language below describes present usable capability and technical leverage. Named humans retain authority for publication, intended use, configured-environment claims, and production acceptance.

## What the six repositories make possible together

[`lims-eln-functional-nucleus`](../lims-eln-functional-nucleus/) places the five
source roles beside one another inside `human-ai-systems-exemplars`. Its version,
manifest, contribution guide, and copy receipt preserve the stronger
constellation organization while recording stable source keys, revision
evidence, filtered exclusions, and checksum parity. The retained origin remains
available through the authorized resolver. The integrated directory is the
cross-repository encounter; the standalone repositories remain the durable
source-history, issue, and release surfaces.

```text
human and practitioner reading
            ↓ shapes interaction, evidence, and role language
program contract ──→ enterprise execution ──┐
        └──────────→ selected-future run ───┼─→ comparative reading
                                            │
governance grammar ─────────────────────────┘
```

Context Canvas pages are design inputs to this flow. Their reading order, visible evidence limits, role-specific agency, and return paths should shape the workbench and comparison dashboard. They also remain useful outputs for collaborators who need to understand a system before operating it.

Across the six repositories, GitHub Actions rests disabled in repository settings at a **$0** budget. Local proof is the standing path. The five active **Control Plane Protected Delivery** rulesets retain deletion, non-fast-forward, one-approval, CODEOWNER, last-push, and review-thread protections with an empty hosted-check set. Each repository retains a manually dispatched proof route, and dependency schedules remain activation templates.

## Three useful planning tracks

### Hold — use the nucleus as it stands

- Keep the governance and selected-future releases stable.
- Run the golden specimen and comparator locally when a collaboration needs evidence.
- Keep the Cloudflare pilot as a direct-view, no-index, closed-framing surface until a named steward authorizes an audience.
- Let new work begin with a practitioner need, a source path, and an observable result.

This track is appropriate when the next collaboration benefits more from use and interpretation than from another platform layer.

### Extend — complete the shared execution loop

- Publish a private installable coordinate for `lims_eln_contracts` 0.3.1; keep the digest-bound standalone adapters until consumers can resolve that coordinate directly.
- Add one versioned golden-result projection inside the existing shared envelope. The current workbench and simulator envelopes use the same scenario identity while their inner result shapes still serve different local purposes.
- Add an explicitly named simulated-verification comparator posture for process-local implementation evidence. Preserve the current observed-evidence lane for configured-environment claims.
- Run comparison through that projection and present classified differences through a concise dashboard reading.
- Extract the next Context Canvas stylesheet family when route ownership or first-paint materially improves; preserve authored source order through an explicit load or deterministic build.

This track turns the existing pieces into one repeatable local encounter without changing their authority boundaries.

### Durable encounter — make one end-to-end path persist

- Compose the FastAPI workbench with PostgreSQL using the existing durable custody, observation, and read-model shapes.
- Let a practitioner run one synthetic specimen from accession through release, inspect raw-byte provenance and vendor reconciliation, compare it with the selected future, and export a redacted receipt.
- Use the Context Canvas interaction and evidence patterns to shape a practitioner-specific dashboard.
- Publish only the bounded reading a named steward chooses. The current Static Assets pilot remains direct-view; a cross-origin iframe enters through a later, explicit replacement of the closed `frame-ancestors` policy with an exact receiving origin and a parent/child capability contract.

This track is the most valuable next investment when the team wants a persistent demonstration that joins domain behavior, evidence, and human interpretation.

## Recommended sequence

1. Exercise the current workbench and simulator against their common scenario identity and resource digests.
2. Release one shared golden-result projection and a labeled simulated-verification comparison posture.
3. Compare those projections locally while the stricter observed-evidence lane retains its present meaning.
4. Add PostgreSQL composition for the same synthetic journey.
5. Shape the resulting comparison reading with Context Canvas design inputs.
6. Decide separately whether the result remains a local handoff, becomes a direct-view Cloudflare reading, or earns a cross-origin embed route.

This sequence advances functionality first. Governance, automation, and publication change when the encounter demonstrates a concrete need for them.
