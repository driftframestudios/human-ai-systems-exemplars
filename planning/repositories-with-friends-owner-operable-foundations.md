# Repositories with Friends — owner-operable foundations and delivery forms

## Purpose

This planning surface describes how a technical collaborator can prepare an
**owner-operable** repository: one that another person can receive, understand,
and continue with an authorized AI collaborator. The immediate route is
intentionally concrete: a
bespoke `context-canvas` repository receives its real site source, a useful
Issue system, and a small collaboration foundation before ownership transfer.
The receiving colleague and AI collaborator then use that live Issue route to
form the first stable private release.

The wider program asks a different question: which parts of that experience
can become reusable delivery forms for engineers who prepare repositories for
colleagues, friends, and collaborators? Milestone 26 owns the portable
foundation and first exercise. [Milestone 27](https://github.com/driftframestudios/human-ai-systems-exemplars/milestone/27)
holds four broader possibilities whose implementation depends on evidence from
real receiving use.

This file carries prospective architecture and re-entry. GitHub Issues retain
current outcomes and acceptance; runnable source retains behavior authority;
the receiving repository retains its implementation decisions.

## Desired state

A receiving owner can begin with ordinary language:

> Create a detailed Issue for the outcome, connect it to the current milestone
> and related Issues, then travel the active Issue route. Explain what each
> move makes possible and return any decision that needs my account authority
> or judgment.

The repository supplies enough orientation, source evidence, and recovery
structure for an authorized AI collaborator to turn that request into a
reviewable change. Identity, rights, credentials, visibility, transfer,
publication, domain, and destructive-recovery decisions stay with their named
human owners. The repository makes those decisions easy to find and prepares
the evidence each owner needs.

Three compact terms recur below:

- **Current front** means the live Issue whose next decision can materially
  advance the route.
- **Receipt** means a concise record of the inspected coordinate, observed
  state, fitting check, coverage boundary, and next owner action.
- **Capability profile** means an optional set of repository abilities selected
  for the current source and receiving use.

### Context Canvas direct-transfer sequence

This private planning surface is the authorized resolver for
`urn:source-key:repository-handoff-exercise-001`. The portable runbook uses
that operator-blind key; this account retains the exact repository and Issue
coordinates needed by authorized collaborators.

The first exercise follows the receiving repository's existing Issue graph:

1. **Issue #1 — receive and inspect the actual site source.** The source
   establishes its framework, package manager, lockfile, routes, behavior,
   external services, and build shape.
2. **Issues #2–#8 — complete the pre-transfer collaboration foundation.**
   Reconcile orientation, reference intake, the Concept Nursery, Visual
   Fidelity Contract, skills, Prompt Capsules, runbooks, AI access, and the
   transfer plan against the observed site.
3. **Issue #9 — transfer repository ownership.** Prepare one owner-readable
   receipt, let the human owners complete or explicitly authorize the transfer,
   then verify the receiving account and repository state.
4. **Issues #10–#16 — let the receiving colleague and AI collaborator carry
   the first substantial collaboration and private release.** This is the
   evidence that the Issue route and repository foundation support continuing
   ownership from repository-held context.
5. **Issues #17–#19 — prepare optional publication and launch.** GitHub Pages,
   domains, public visibility, and launch remain choices for the receiving
   owner when the private site is ready.

This sequence places transfer at the point where the repository is useful and
continuable. The receiving owner gains genuine authorship of the first release
while the preparing collaborator supplies a sound starting point.

## The architecture has four distinct owners

| Owner | Job | Authority boundary |
| --- | --- | --- |
| `repository-handoff-readiness` skill | Assess current standing, select the smallest fitting profile, and identify the next owner action | User intent, live source, the active Issue, and granted tools govern every action |
| `repository-handoff-foundation` artifact | Supply a versioned source-neutral set of files, profiles, templates, and materialization inputs | Incoming site source owns its runtime and dependency direction; owner-edited live Issues remain current |
| `site-repository-build-and-handoff` runbook | Carry a known route from source-awaiting preparation through handoff and one receiving collaboration cycle | The runbook orders existing owners; it does not grant transfer, publication, credential, or destructive-action authority |
| Live Issue graph | Hold current outcomes, acceptance, relations, and next receivers in the repository being prepared | Each Issue keeps its own contract; the seed remains a bootstrap and recovery input |

A task-bound projection may bind the portable skill and runbook to one named
repository, Issue, tool set, and exit event. It remains one derivation edge
from the portable contracts and rests when the receiver accepts the handoff.

## Additive capability profiles

Profiles are selectable capability sets. They express independent abilities
instead of ranks. A repository may
need only the first profile, or it may compose several in the order supported
by its source and owner decisions.

1. **Foundation** — orientation, collaboration guidance, Issue route, Concept
   Nursery, reference intake, and a dependency-free structural check.
2. **Received site** — source receipt, observed technology profile,
   reproducible preview or build, and a source-grounded Visual Fidelity
   Contract.
3. **Stable private release** — fitting tests, privacy and trust review,
   inspectable artifact, release identity, and recovery coordinate.
4. **GitHub Pages** — a source-native artifact and held deployment route the
   owner can activate.
5. **Service-backed extension** — server, data, authentication, secret, or
   cross-repository delivery selected when observed behavior calls for it.

## Event-triggered context routing

Repository guidance is most useful near a decision. The foundation should
surface a small context cue when an observable event changes the next action,
then return to the live owner:

| Repository event | Context to surface | Decision it should support |
| --- | --- | --- |
| A request arrives before a receiving Issue exists, or changes the current chain | Issue-writing capsule and current Issue relations | Create or revise one outcome-bearing Issue and name its next receiver |
| Acceptance evidence satisfies an Issue or reveals a separate outcome | Acceptance criteria, current evidence, and open boundary | Prepare closure or form one distinct follow-on Issue |
| A pull request merges | Branch ancestry, current branch list, and recovery coordinate | Offer exact merged-branch cleanup to the authorized owner |
| Structure, commands, ownership, or public routes change | Root and nearest README graph plus `AGENTS.md` | Reconcile the smallest stale orientation surface |
| A manifest or lockfile changes | Declared scripts, lock state, advisory and license routes | Run the focused install, lint, build, advisory, license, or consumer check that establishes the new state |
| Rendered behavior changes | Affected route, viewport, interaction, and accessibility owner | Select the smallest browser observation that answers the visitor question |
| A release candidate forms | Secret, attribution, privacy, artifact-identity, tag, and recovery owners | Prepare one reviewable release receipt and return held decisions |
| Publication or transfer approaches | Platform settings, collaborators, automation, protections, domains, and plan-dependent features | Reconcile the exact account-level state with a named human owner |
| Resting material becomes timely | Concept Nursery, reference ledger, and current Issues | Promote it to an Issue, keep it resting with a return signal, or retire it |

These cues are invitations tied to evidence. The owner can accept, revise,
defer, or decline the proposed action.

## Bounded drift reconciliation

“Self-healing” is most useful here as **bounded drift reconciliation**. The
repository can detect and safely repair mechanical state it clearly owns while
placing authored, account-level, and security-sensitive differences in a
reviewable plan.

| Drift class | Default response | Examples |
| --- | --- | --- |
| Generator-owned and deterministic | Compare, explain, and reconcile through the named generator | Generated index, derived manifest, repeatable route table |
| Structurally checkable with several valid outcomes | Produce a plan and smallest proposed patch | README routes, Issue-seed comparison, missing optional module |
| Owner-authored or dependency-bearing | Preserve current state and prepare a reviewed decision | Site source, prose, lockfiles, package versions, live Issues |
| Account-, identity-, or secret-bearing | Keep values with their authorized owner and return the exact action needed | Credentials, repository transfer, visibility, domains, signing, destructive recovery |

Every repair path retains a known-good coordinate and states what the selected
check establishes. A quiet scanner, absent assertion, or generated diff leaves
adjacent behavioral and human-acceptance claims open for their own evidence.

## Source and authority map

| Surface | What it establishes |
| --- | --- |
| Received site source and generated artifact | Behavior authority and the exact artifact at the inspected revision |
| Source-native tests and browser observations | Exercised runtime or visitor states and their coverage boundaries |
| Root and nearest README, `AGENTS.md`, skills, and runbooks | Standing orientation and reusable collaboration routes |
| Technology and foundation profiles | Observed stack facts, selected modules, and their activation conditions |
| GitHub Issues and pull requests | Current outcomes, acceptance, proposed changes, review, and next receivers |
| Planning | Options, architectural relationships, and future delivery forms |
| Threadkeeping | Settled rationale, decision-changing observations, and re-entry memory |
| Repository owner | Identity, rights, credentials, visibility, transfer, publication, domain, and destructive-recovery decisions |
| Receiving colleague and authorized AI collaborator | Post-transfer implementation, first private release, and observed usability of the handoff |

The foundation validator establishes structural presence and declared
relationships. Source-native tests establish only the behaviors they exercise.
Transfer acceptance and useful continuing ownership remain human and
receiving-collaboration observations.

## Milestone 27 — four future delivery forms

[Milestone 27 — Repositories with Friends — Delivery Forms and Owner-Operable Archetypes](https://github.com/driftframestudios/human-ai-systems-exemplars/milestone/27)
is future-facing and non-blocking for Milestone 26. Each concept can be
created, queued, observed, folded into another owner, or rested independently.

### 1. [Repository Foundation CLI — Issue #418](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/418)

An engineer-facing initializer could unfold the settled foundation into a
new or existing repository, report Node, npm, Git, and GitHub CLI standing,
verify a received lockfile, run authorized installation and advisory checks,
and materialize the Issue seed. The core semantics belong in #415 first. A
package becomes worthwhile after repeated handoffs demonstrate stable
mechanics and real turn savings.

A fitting npm carrier can use the platform's conventional initializer mapping:
`npm init @radiantnull/repository-foundation@<version>` resolves to a scoped
`@radiantnull/create-repository-foundation` package. Its plan/apply/verify
route should preserve owner-edited files, keep lifecycle scripts as an
explicit decision, and offer advisory findings. An accepted receiving Issue
authorizes any dependency-version change.

### 2. [Decision Operations Workbench — Issue #419](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/419)

A separate repository program could serve executives, project managers, and
other decision owners who need forecasting, data analysis, scenario records,
and continual handoffs from technical colleagues. Its Python environment can
travel through `uv`, with starter Issues that connect evidence, assumptions,
decision rights, and revisable forecasts. This is a distinct product that
should form from a real receiving use. The colleague's site repository keeps
its direct showcase purpose.

### 3. [RadiantNull Discovery Anchor — Issue #420](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/420)

A small public repository could provide a stable discovery root for published
skills, foundation releases, compatibility notes, and authoritative source
routes. It should stay quiet by default: versioned source repositories retain
semantic authority, while the anchor helps collaborators find the current
owner and fitting release. Formation waits for settled publication identity
and a clear relationship with `schemas.radiantnull.com`.

### 4. [Owner-Operable Exemplar Seed — Issue #421](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/421)

One self-contained Human–AI Systems Exemplar could become a compact repository
seed with its own visitor surface, collaboration vocabulary, Issue route, and
small dependency foundation. The Cross-Functional Investment Studio is a
strong first candidate because its rail, editable model, and decision-bearing
handoff already form a coherent experience. This concept should follow #417:
it can become the second materially different receiver whose use shows whether
the handoff skill is ready for `stable` standing.

## Official platform constraints informing the route

These sources constrain the delivery design; the receiving repository and
observed exercises decide the implementation details.

- [GitHub — Transferring a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository): a transfer carries the live repository and its collaboration history into new ownership. This supports direct transfer for the current colleague route and makes post-transfer settings reconciliation a material phase.
- [GitHub — Creating a repository from a template](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template): a template creates a new repository from the template's files and branch selection. The live Issue route therefore needs its own materializer when this delivery form is chosen.
- [npm — `npm init`](https://docs.npmjs.com/cli/init.html/): npm's initializer convention supplies the possible `create-*` carrier for an engineer-facing CLI.
- [npm — `package.json`](https://docs.npmjs.com/cli/v12/configuring-npm/package-json/): `files`, `bin`, version, engines, and related metadata define what a future initializer actually distributes and invokes.
- [npm — `npm ci`](https://docs.npmjs.com/cli/commands/npm-ci/): clean, lockfile-bound installation is the fitting reproducibility check after a received Node project supplies its lockfile.
- [npm — `npm audit`](https://docs.npmjs.com/cli/npm-audit/): advisory inspection can inform an owner-readable dependency decision while update authority stays with the receiving Issue.
- [uv — Tools](https://docs.astral.sh/uv/concepts/tools/): `uvx` can run a packaged Python tool in an isolated environment, which fits a future Python-based workbench or helper while the host's base Python installation stays intact.
- [GitHub CLI — `gh issue create`](https://cli.github.com/manual/gh_issue_create): a future Issue materializer can use the supported CLI surface after plan output and explicit apply authority are established.

## Evidence and lifecycle

The `repository-handoff-readiness` skill and
`site-repository-build-and-handoff` runbook begin at `working`. They become
`exercised` only after the Context Canvas transfer and one ordinary
post-transfer Issue-to-change cycle. A second materially different receiving
repository can support `stable` standing. Self-authored scenarios, file
presence, and internal consistency establish contract structure. Receiving
use establishes whether the route was useful.

Milestone 26 can complete when the Context Canvas receiver demonstrates
continuity and the reusable artifacts absorb any decision-changing friction.
Milestone 27 proceeds concept by concept; each delivery form can settle on its
own evidence and receiving use.
