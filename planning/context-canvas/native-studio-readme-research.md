# Native Investment Studio README research

[Issue #994](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/994) asks how a first-time reader can run and understand the Studio while a returning contributor can find the owner of a change. The existing README places branch history and chapter-by-chapter behavior before the first run. That history has already drifted once. [PR #966](https://github.com/driftframestudios/human-ai-systems-exemplars/pull/966) reached `main` while the README still described promotion as pending. The Studio already has an implementation reference, an experience journal, visual contracts, and focused tests. Each gives the revised README somewhere specific to send a reader.

## What the evidence changes

| Evidence | What it changes for the Studio |
| --- | --- |
| **Official platform guidance.** GitHub treats the README as first contact and documents branch-relative links, images, and heading anchors. [GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) | Give readers purpose, startup, and a useful first task on arrival. Use relative links and image paths for material that travels with the checkout. GitHub describes platform behavior. The Studio still decides its headings and depth. |
| **Expert documentation practice.** Diátaxis distinguishes learning, task completion, reference, and explanation. Tom Manshreck describes writing for a specific audience and reviewing documentation alongside source at Google. [Diátaxis](https://diataxis.fr/), [Software Engineering at Google, chapter 10](https://abseil.io/resources/swe-book/html/ch10.html) | Put a worked edit in the entry README. Route deeper tasks to an exploration guide and keep reference detail with the existing implementation reference. The framework informs reader tasks. The package already has owners for several of them. |
| **Interaction design guidance.** Jakob Nielsen describes showing common actions first and making specialized options discoverable on demand. [Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | Link directly to the two deeper README routes and the existing reference. Applying UI disclosure guidance to document navigation is a design inference. A first-time walkthrough can reveal whether link labels and reading order work here. |
| **Technical leadership practice.** GitLab's published principal framework emphasizes explaining tradeoffs and breaking complex work into small deliverables. Will Larson recommends grounding design in a specific problem, considered solutions, and the selected approach. [GitLab principal framework](https://handbook.gitlab.com/handbook/engineering/careers/matrix/principal/), [Writing engineering strategy](https://staffeng.com/guides/engineering-strategy/) | State who owns each changing fact, keep the runtime boundary verifiable, and make the decision and implementation independently reviewable. These sources guide judgment and review scope. The Studio's size and existing owners set the amount of structure. |
| **Practitioner discussion.** In an Apache AGE maintainer's README discussion, readers asked for exact invocations and enough imagery to recognize the interface. Other participants favored a concise entry and suggested observing a newcomer run it. [Ask HN discussion](https://news.ycombinator.com/item?id=26537805) | Use two screenshots tied to real tasks and test the documented quickstart. The thread supplies firsthand preferences and a review method. It leaves the ideal screenshot count and placement open. |
| **Comparable repository.** Source of Truth for Life Sciences uses a documentation index (`docs/README.md`) and nearby owner READMEs. Its public receiving README pairs a screenshot and local run with links organized by reader intent. | Borrow the purpose, runnable example, and intent-based routes. The Studio's static About host needs one HTTP command and a browser. The reference project's build, data, deployment, and publication routes serve its own application. |

## Four ways to organize the README

| Approach | Useful part | Cost in this package |
| --- | --- | --- |
| Reorder the existing single README | Put first-run material before the reference and keep every detail one scroll away. | Large chapter inventories still compete with startup and repeat the journal and implementation reference. |
| Use a short README with direct links to existing owners | Keep the entry fast and send experienced contributors straight to authoritative files. | A reader who has run the example still needs a step between basic use and the full reference. |
| Add a README for each chapter or concern | Give recurring chapter work a nearby entry with controls, ownership, and fitting checks. | Six chapter pages and several cross-cutting topics would create more routes to maintain. Shared state and recovery span those chapters. |
| Add two task-oriented README routes | Give people using the example and people changing code a short path to the material they need. | Two more pages need a clear maintenance rule. They earn their place through useful instructions, specific source links, and a return to the entry. |

## Recommendation

Use two task-oriented routes. Keep the single-page approach's complete first run in the root README. Follow the direct-link approach for the implementation reference, design decisions, and live GitHub work. Borrow chapter-level navigation inside one exploration guide and place it next to a contributor route that maps one edit from the page through state, drafts, and checks. Keep the JavaScript files in their existing locations.

Show Coordination early enough for readers to recognize the sprint board, then show Investment where the README explains the consequence of a session edit. Capture both from the bundled example. Update an image when visible controls or readings change what its caption teaches. When specifying file exchange and recovery, name what persists in the tab and what the download contains beside the corresponding action.

The Studio source owns behavior, the technical reference owns detailed contracts, the experience journal owns rationale, and GitHub owns active status. Two focused pull requests against `main` give the maintainer independent review of the recommendation and the documentation. Each can stand on its own. Review the README, then use its quickstart to exercise Apply and Undo, check the relative links, and compare the proposed tree with the base. Those observations cover source navigation and the tested local journey. A first-time reader's choice of route and understanding of edit lifetime need a cold walkthrough. Additional chapter READMEs earn consideration if users repeatedly struggle to find the same chapter's controls or code.
