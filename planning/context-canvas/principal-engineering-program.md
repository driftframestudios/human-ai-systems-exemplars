## Schema, ontology, and hybrid human-AI collaboration

The Canvas already contains structured state, JSON-LD, semantic tables, source manifests, and prototype inspectors. Principal-level schema work should make those resources dependable without asking a machine artifact to become the human explanation.

The governing relationship is:

```text
human-readable contract
        ↓ defines meaning and authority
versioned schema or vocabulary
        ↓ constrains exchange
positive and negative fixtures
        ↓ demonstrate expected behavior
visitor or prototype state
        ↓ produces an inspectable instance
semantic HTML equivalent
        ↓ keeps the state available across capability differences
bounded validation result
        ↓ answers the receiving decision
```

Required schema posture:

- Use immutable versioned HTTPS identifiers for settled schema versions; use an explicit mutable alias only when its movement is documented.
- Keep `$id`, canonical documentation, content type, CORS, cache policy, and repository source in agreement.
- Prefer closed objects with `additionalProperties: false` or `unevaluatedProperties: false` where extension is not an intended capability.
- Bound string lengths, arrays, nesting, imported bytes, and accepted identifiers before an imported state reaches the DOM.
- Validate representative external examples directly. Keep a few in-memory rejection probes for consequential core and extension boundaries; migration and round-trip fixtures follow an actual second version or consumer.
- Treat JSON-LD as a semantic representation of visitor content, not collaboration state or an internal proof ritual.
- Keep a human-readable page authoritative for contested meanings, evidence boundaries, and accountable human decisions.
- Preserve semantic HTML or tabular twins for diagrams and interactive state that must survive scripting, framing, assistive technology, printing, or machine retrieval differences.

The future constellation repository and the secured `@driftframe` namespace can become appropriate owners for shared vocabulary, schemas, registries, and validation packages. They should receive a contract only after reuse is real. Context Canvas-local aliases are preferable to premature package extraction.

The first applied route now lives in the [schema contract research and implementation plan](../schema-contract-research-and-implementation-plan.md). ## Prototype capability and cross-subdomain contract

Every embedded prototype should declare capabilities instead of accumulating sandbox tokens by precedent. A small manifest entry can name:

- scripts;
- forms;
- popups and whether the popup may escape sandbox restrictions;
- downloads;
- clipboard;
- storage or origin-bound APIs;
- top navigation;
- parent communication;
- external network destinations;
- expected semantic and no-script equivalents.

The parent then derives or validates `sandbox`, `allow`, `referrerpolicy`, loading, title, and any framing guidance. Capabilities that are absent remain unavailable.

Separate subdomains improve containment but do not replace the sandbox. Once prototypes move off the Canvas origin:

- the parent owns which origins may be framed through Content Security Policy;
- the child owns which parents may frame it through `frame-ancestors`;
- Cross-Origin Resource Sharing is enabled only for resources that genuinely require cross-origin reading;
- `postMessage` checks exact origins and `event.source`, uses a versioned closed envelope, limits size, and ignores unknown message types;
- parent-initiated requests and child-reported observations remain distinguishable;
- navigation remains an explicit visitor action, ordinarily opening onward routes outside the embedded surface when recursive framing would be confusing.

The first protocol should carry only a capability that has become necessary. Likely candidates are `ready`, measured content height, selected state, or an explicit request to open a leave-behind. A universal event bus would be architecture without a receiver.

## Security and input safety

Static hosting narrows the attack surface but does not eliminate it. The consequential boundaries are imported data, inline execution, embedded capabilities, external resources, cross-origin messages, and publication mistakes.

Recommended controls:

- Parse imported JSON as data, validate it against a closed schema, cap bytes/depth/collection sizes, normalize stable identifiers, and render with DOM text APIs rather than interpolated HTML.
- Replace dynamic handler strings with delegated event handling on touched prototypes.
- Establish an active-content scan for SVGs, HTML downloads, and copied prototype packs.
- Preserve `rel="noopener noreferrer"` for outward tabs and describe new-tab behavior in the prototype.
- Move public-page inline executable code toward external, hashable files; retain self-contained prototype exceptions only when their value is explicit.
- Define a report-only Content Security Policy before enforcement, then narrow `script-src`, `style-src`, `img-src`, `frame-src`, `connect-src`, and `frame-ancestors` from observed requirements.
- Keep Cloudflare WAF rules versioned and reviewed. WAF posture should protect an origin boundary, not compensate for unsafe DOM construction.
- Prevent directory indexes, editor metadata, planning, threadkeeping, source ZIPs, local manifests, and historical server logs from entering the public artifact unless explicitly declared.
- Add secret and high-entropy scans even though the intended runtime is static.

### When to open an Issue

Open an Issue when all four are true:

1. The result can be described as an observable change or answered investigation.
2. The boundary is small enough that a collaborator can complete or deliberately close it.
3. Acceptance evidence can be named before implementation.
4. The work benefits from assignment, discussion, dependencies, cross-references, or automatic linkage to a pull request.

Keep the item in planning when it still needs competing framings, source research, multiple implementation packets, or a decision about what problem is being solved.

GitHub supports sub-issues, blocking relationships, labels, milestones, and bidirectional Project views. Use those only after the underlying Issues are useful. Do not build a Project vocabulary in anticipation of work that has not appeared.

### Handoff invariant

Each active item has one operational owner:

- Planning owns the larger terrain.
- An Issue owns immediate actionable state.
- A pull request owns the proposed diff and review.
- Git and deployment own the landed and served state.
- Threadkeeping owns rationale and re-entry, not live task status.

Other surfaces link to that owner and record only the consequence that matters locally. When a pull request closes an Issue, the planning matrix changes only if the horizon or dependencies changed. This prevents five nearly synchronized status fields from becoming five subtly different truths.

Practitioner Probes offer an effective way to turn a planning row into an implementation-quality investigation without pretending that every question deserves code.

For a selected terrain:

1. Name the technical question in language a practitioner would actually use.
2. Explain who or what bears the effect.
3. Trace the causal mechanism through browser, cascade, schema, build, origin, or organization behavior.
4. Select a complexity level proportionate to the decision—from direct check through cross-system reasoning.
5. Name observable evidence and credible sources.
6. Extract an instruction another collaborator or AI system can apply.
7. Decide whether the result returns to planning, becomes threadkeeping, opens an Issue, or changes source.

Useful next probe families include:

## Details often forgotten in static-system programs

- Source order is an API when no explicit cascade architecture exists.
- GitHub Pages project paths differ from domain-root paths; root-absolute links can work locally and fail after publication.
- If automatic hosted checks return later, required-check and skip behavior must preserve an explicit mergeable resting state.
- A static site can still expose internal artifacts simply by publishing the wrong directory.
- `allow-scripts` plus `allow-same-origin` is a consequential combination for same-origin frames.
- Cross-origin isolation, CORS, CSP framing, and sandbox permissions solve different problems.
- Accessible names can disappear when visible tooltip text is hidden from the accessibility tree.
- Page-width overflow checks do not detect content clipped inside an overflow-hidden component.
- `min-width: 0` and intrinsic table sizing are recurring narrow-layout concerns.
- Print and no-script modes can expose stale or missing records even when the interactive view is correct.
- External links inside an iframe can replace the embedded surface or be refused by the destination unless navigation behavior is explicit.
- Generated reports need the same table semantics, escaping, source boundaries, and state truthfulness as their live prototypes.
- Canonical URL, sitemap URL, Open Graph URL, and deployed URL need one authority.
- A default 404, MIME mismatch, or invalid TLS certificate can make a technically correct schema effectively nonexistent.
- Deleting or reorganizing threadkeeping paths can destroy more continuity than it creates tidiness.
- Optimization output without readable source and provenance weakens future human-AI collaboration.
- Remote-proof configuration consumes collaboration attention and should remain smaller than the evidence it produces.
- Artifact retention, cache duration, log retention, and screenshot volume are cost decisions as well as technical settings.
- Existing local full-page images average about 1.87 MiB, so the current 42-route, three-viewport phase may approach 236 MiB. That volume remains manageable under ignored `.visual-runs/` for this cycle. Portable storage returns after the human calculates likely Cloudflare transformations and explicitly reopens the decision.
- Dependency updates and action pins need a cadence even when runtime dependencies remain zero.
- A rollback is not real until an earlier source revision can recreate and redeploy the same artifact.
