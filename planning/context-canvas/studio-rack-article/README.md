## Two phases, five beats each

The two readings revisit the same consequential episodes from different
questions. Solution asks how the team shaped the visitor experience.
Implementation asks how the team made the experience usable, recoverable and
maintainable. Design and implementation continued to affect each other throughout
the history; the phase boundary is a reading distinction rather than a calendar
cutoff.

The closest five-beat precedent is
[Who to Believe](../../../context-canvas-project-surface/context-canvas/who-to-believe-reviews-platform.html):
**Debrief → Bottleneck → Intervention → Outcomes → Repeatability**, repeated for
Solution and Implementation. The
[paired Debrief contract](../../../visual-fidelity-contracts/dual-track-debrief-composition.md)
supplies written movement labels, orientation, source posture and a closing
evidence boundary for each phase. The table below specifies beat jobs, not prose.

| Beat | Solution: shaping the experience | Implementation: making it dependable |
| --- | --- | --- |
| a · Debrief | Introduce the visitor purpose, the two original instruments and the developing showcase. | Locate inherited instruments, shared analysis, the chapter bridge, native JavaScript and the About receiver. Introduce the folder map. |
| b · Bottleneck | Explain presentation and coordination constraints, including embedding, scattered controls and misleading precision priorities. | Explain shared-state, reference-integrity, draft/recovery and source-ownership pressures, including re-entry across sessions and models. |
| c · Intervention | Follow human-selected concepts, materially different alternatives, the runnable rack study, aesthetic corrections and selected adoption. | Connect canonical state, controllers, shared controls, focused tests, Visual Fidelity Contracts, planning and journaling. |
| d · Outcomes | Show visitor abilities at the accepted endpoint, retained alternatives and remaining conditions. Keep the endpoint open until selected. | Show reviewed integrations, bounded behavior observations, preserved specimens and recoverable state. Use history and material measures as navigation. |
| e · Repeatability | Extract practices for agreeing on desired visitor abilities, preserving specimens, comparing options and revising priorities. | Offer a portable source-reading and journaling routine, with one current owner, observation, receiver and reopening condition. |

## Journaling that a later collaborator can use

The interactive repository map must show relationships as well as folders:

| Surface | Receiving job | Authority boundary |
| --- | --- | --- |
| JavaScript, HTML, CSS and runnable artifacts | Establish current behavior and its owning modules. | Historical prose is reconciled against this source. |
| Nearest README | Supply standing orientation, quickest proof and onward owners. | Detailed history stays with its journal or reviewed record. |
| `planning/` | Hold options, experiments, acceptance direction and prospective bridges. | A proposal's presence does not establish runtime adoption. |
| Experience journal and `threadkeeping/` | Preserve decisions, reasons, supersessions and exact re-entry. | A prior decision can be reopened by current source or human direction. |
| GitHub Issue and PR | Carry current work state, scope, reviewed change and next receiver. | A closed or merged record retains its named evidence boundary. |
| `.agents/skills/` and runbooks | Carry portable procedures and conditional routes. | Current task authority and source evidence govern their use. |

An entry earns its place when a decision changes the route. Keep the decision,
reason, affected source/revision, owner, fitting observation, superseded direction,
next receiver and reopening condition together. Update the existing owner rather
than multiplying parallel receipts. Ordinary file edits and complete transcripts
need no automatic journal entry.

A task can encourage this behavior with a compact instruction:

> Begin by reconstructing the current branch, worktree, Issue and runnable source.
> Read the nearest README, relevant planning and settled journal entries. When a
> consequential decision changes the route, update its existing journal with the
> reason, source revision, observation, supersession and next receiver. At handback,
> name one exact re-entry move. On a later session, reconcile that record with
> current source before continuing.

This route lets different models and sessions recover useful context from
inspectable records. Model identity, assumed recollection and reuse count supply
no substitute for the receiving source observation.
