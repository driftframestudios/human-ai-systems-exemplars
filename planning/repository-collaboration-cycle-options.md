## Hydrate — the session-opening result worth carrying forward

This cycle began with a useful orientation docket: reconstruct current truth,
classify candidate Issues, assign bounded support, synthesize the returns, and
close with scope, changes, validation, risk, and a next receiver. The docket
helped, yet several completed collaboration cycles revealed a stronger opening
surface: orientation and execution belong to one re-entrant route when the
collaborator is expected to deliver a material repository result.

The wished-for opening docket therefore names five relationships at the start:

1. exact repository and Git coordinate;
2. live Issue, pull request, milestone, and acceptance owner;
3. mutation and external-action authority;
4. expected evidence lane and any human-held decisions; and
5. support capacity as available, resting, or unknown.

The [Repository collaboration cycle runbook](../.agents/runbooks/repository-collaboration-cycle.v0.1.md)

[`repository-collaboration-cycle` skill](../.agents/skills/repository-collaboration-cycle/SKILL.md)

[#153](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/153)

The selected architecture combines the first three: a compact launcher enters
one full-cycle spine, then domain overlays load conditionally. A separate
receiver-specific suite earns reconsideration when a receiver develops stable,
materially distinct lifecycle semantics. Machine preflight enters after
repeated drift identifies a deterministic check with real turn savings.

## Support capacity — one conditional branch

Spark can receive bounded microtasks through a capacity-dependent branch.
Repository source owners retain lifecycle authority, so one stable repository
cycle carries re-entry, execution, evidence, and delivery:

```text
current truth
  -> route selection
  -> conditional environment preparation
  -> primary implementation or finding
  -> proportionate verification
  -> one handback and exact re-entry
```

When capacity is available, `bounded-support-routing` forms one finite packet
for a patch, wording pass, focused test, evidence extraction, or recovery
observation. The primary collaborator continues to own synthesis and final
evidence. When capacity rests, primary work continues. A packet is collated
for later only when its pinned surface, requested result, and stop condition
are likely to retain decision value.

An `awaiting_capacity` packet activates through four refreshed facts: current
revision, Issue acceptance, continuing need, and renewed action mode. This
gives the later receiver current premises at activation. Spark-specific
platform facts remain one conditional reference in the bounded-support skill,
where they can change independently of the repository runbook.

## Evidence-lane preparation — inspect, then prepare

The root repository owns the locked setup:

```sh
node --version
npm ci --ignore-scripts
npm run playwright:install
```

Node and installed packages are inspected first. The locked dependency install
enters when the selected checks require packages and the current task permits
the download. The Playwright script adds the repository-supported Chromium
runtime when rendered evidence is part of acceptance. A named cross-engine
question can add the locked Firefox and WebKit runtimes and record their
versions. Browser downloads affect local disk and behavior while tracked
source remains unchanged, so the handback carries that environment note.

This cycle found one orientation drift: the root README had moved to
`npm ci --ignore-scripts` while the Context Canvas README still named
`npm install`. Aligning that local README with the root locked command gives
cold collaborators one setup route. When a system-level browser capability
lives in an authorized browser or CI receiver, the exact check routes there;
the related behavior claim stays open until that observation arrives.

## Instruction architecture — desired state as the attractor

The named Notion workspace guidance, **Semantic Attractor Design —
Negation-Aware Instructions**, and its repository carrier at
[`field-guide/src/semantic-attractors/`](../field-guide/src/semantic-attractors/Output%20Guidance%20Documentation%20%E2%80%94%20Semantic%20Attractor%20Design%20%E2%80%94%20Negation-Aware%20Instructions.md)
shape the runbook and skill as authored guidance.

The implementation uses four writing patterns:

- the desired receiving state leads each artifact and phase;
- a hard authority, privacy, safety, or publication boundary sits beside the
  useful state it preserves and the route that can release continuation;
- each evidence statement leads with what the signal establishes, then names
  the adjacent claim and its fitting observation; and
- support-capacity language describes the primary route that remains active
  while a secondary receiver rests.

This discipline preserves materially meaningful negation where the boundary
itself carries the meaning. Quoted source, code, identifiers, and existing
governed terminology retain exact fidelity.
