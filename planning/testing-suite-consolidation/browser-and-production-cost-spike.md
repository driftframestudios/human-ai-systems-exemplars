# Shorter browser feedback and production carrier builds

Research decision, 20 November 2026. The source is merged PR #971 at `8b56400`. The hosted timings are from its final head, `a8591a0`. The recommendation covers developer feedback, the explicitly selected three-engine proof, and the cPanel projection and transfer tools. Each has a different cost and acceptance condition.

## Decision

Keep the existing focused npm commands for everyday work. For a complete browser check, optimize the Ubuntu package installation first, then the most expensive browser observations. For production, give the projector and transfer reader one bounded Git blob reader per operation. Use standard JavaScript collections for the few joins that still scan whole lists. These changes fit the current tools and require zero new npm dependencies.

## Five design choices

| Choice | Where it helps | Gotcha and decision |
| --- | --- | --- |
| **1. Verified Ubuntu package reuse** | Full browser runs on standard runners. Extend the working media-job pattern to the packages required by the locked Playwright engines. Resolve one package plan, restore its archives, let APT validate and install them, then install the pinned browsers. | Key by architecture, Ubuntu and runner image, selected engines, locked Playwright version and resolved package versions. PRs restore, a trusted successful run publishes, and cold misses use normal installation. Compare restore **plus** verification/install with a download. The media cache covers FFmpeg and demonstrates the pattern. It does not measure a browser-cache hit. | **2. A version-matched browser image** | A fallback if package-cache misses or APT install time still dominate. Compare one digest-pinned image containing the matching browser builds and Linux dependencies. | Include cold image pull, Node admission, fonts, sandbox behavior, patching and image maintenance in the comparison. | **3. Focused feedback and equivalent full coverage** | For a page-only change use the relevant source contract and browser family first. For the CSS proof, one snapshot reads each element’s geometry and resolved CSS properties, including active pseudo-elements. If allocation dominates, digest in bounded blocks. If name sorting dominates, reuse verified equivalent property lists with a fallback for differences. ## Production route and complexity

The npm commands compose separate operations. The Core and Canvas packagers feed the aggregate. The cPanel planner reads the selected Git tree, resolves public references and assets, projects CSS and builds the output manifest. Build and check write and verify that plan. Carrier staging adds its TSV index. Carrier checking reconstructs the source plan and compares the committed release. Transfer build and verify start from an annotated carrier tag. They can package an accepted release without rebuilding the website. The standalone public-reference materializer also serves a broader source inventory than the cPanel selection. [Command definitions](../../package.json) · [Production release sequence](../../deployment/cpanel/README.md) · [Transfer ownership](../../deployment/cpanel/SHELL-FREE-ARTIFACT-DELIVERY.md)

The scores below describe the visible algorithms on admitted inputs. F is the number of files in the operation, G the number of entries in the source Git tree, B the total input and output bytes handled, and Z the compressed archive size. Path lengths and entry counts have production limits. Map and Set lookups assume expected constant-time access for bounded keys. Sorting is charged separately. Library parsing, CSSO optimization, Git decompression, filesystem latency and zlib compression have their own costs. Peak live space and cumulative copying can differ substantially.

| Operation and owner | Time and space today | Improvement and invariant |
| --- | --- | --- |
| **Iframe aggregate** — `build:iframe-routes`, also constructed by the production planner | The resource walk uses a visited set and a queue, roughly O(vertices + edges) plus scanning asset bytes and sorting receipts. Core’s hub rewrite scans the whole hub once per prototype, O(routes × hub length). The plan retains package buffers and metadata, O(B + files + edges) for these structures. | At the measured 0.24s, keep the existing traversal. If hub cost grows, rewrite hrefs in one scan with a target map and per-target occurrence counts. Preserve the exactly-once requirement, per-route closure checks and sorted output. [Core hub](../../tools/package-iframe-routes.mjs) · [Closure walk](../../tools/iframe-route-package-engine.mjs) |
| **Public-reference admission and HTML materialization** — standalone and embedded in production | Token replacement already uses keyed destination lookups. For one page with I iframe carriers and K distinct iframe keys, fallback validation filters I carriers for each key, O(IK), quadratic when K grows with I. Deriving M primary route bindings by filtering F manifest records costs O(MF). In addition there are the document scans, JSON parsing, output bytes, and key sorting. Peak inventory space is O(B + token occurrences + binding and owner records), plus parser workspace. | Group each iframe key’s embed, anchor and fallback evidence in one pass, O(I) time and O(K) index space. Build an invocation-local owner index in O(F) and resolve M owners in expected O(M). Keep counts or lists for ambiguous owners. Preserve exact global coverage for standalone publication, selected-key coverage for cPanel, and all escaping and carrier-policy checks. [HTML inspection](../../tools/materialize-public-references.mjs) · [Route derivation](../../tools/public-route-reference-contract.mjs) |
| **Production composition** — `build:prod-projection` and `check:prod-projection` | Git tree indexing is O(G). Source reading and hashing scale with B, plus one process per selected blob read. Canonical output ordering adds O(F log F). Each primary HTML file searches Canvas routes. Each asset tests all family selectors, with additional linear searches inside explicit path lists. Markdown with R replacements in a document of length L can copy O(RL) characters when strings are flattened. CSSO is a separate cost. Peak retained plan space is O(B + G + F + recorded relationships), plus parser and CSSO workspaces. | Batch by admitted object ID. Preindex source path to Canvas route and explicit asset paths to candidate families. Keep prefix selectors separate and retain ambiguity diagnostics. For link-heavy Markdown, append untouched slices and replacement text in source order, then join once. Preserve authored bytes outside the spans. The CSS projector makes just three grouped link replacements in the current profile. [Planner and rewrites](../../tools/build-prod-projection.mjs) |
| **Persist, stage and check the committed carrier** — `stage:prod-carrier` and `check:prod-carrier` | The stage adds a sorted TSV, hashes outputs, writes and verifies temporary files, then renames. Its work beyond the plan is O(B + F log F), with O(F + index bytes) additional index space and payload-sized disk staging. The committed check additionally scans the tracked tree and compares two sorted path lists using `includes` in both directions, O(F²) for matching populations, before verifying blobs. | Merge the two sorted lists with cursors in O(F) after sorting, preserving ordered missing/extra diagnostics. Existing independent byte and mode comparisons, source-parent checks and transactional replacement continue to carry the release proof. [Carrier stage and verification](../../tools/build-prod-projection.mjs) |
| **Tagged transfer build and verify** — `build:prod-carrier-transfer` and `verify:prod-carrier-transfer` | Each loads the tagged tree and scans all previously accepted paths for every portable-name collision, O(F²) time and O(F) transient keys at peak. The ZIP writer sorts names, hashes/checksums bytes and deflates entries. Inspection inflates, compares and sorts entry ranges. Beyond tag loading, this costs O(F log F + B + Z) plus codec work. Payload, compressed buffers and expanded verification bytes can coexist, O(B + Z + F) plus codec workspace. | Reuse the normalized-path Set pattern already in the ZIP writer. Keep the original-path map for exact byte lookup. Batch tagged blob reads too. Stream entries only when measured peak memory warrants the added lifecycle work. Keep UTF-8 order, deterministic headers, bounds, digest checks, archive inspection and independent verification against the selected tag. [Tagged loader, ZIP and verifier](../../tools/package-prod-carrier-transfer.mjs) |

The About HTML tokenizer has another conditional O(raw-text elements × document length) term because it lowercases the whole document inside each closing-tag lookup. A future optimization should scan ASCII tag names without changing original string offsets. Its two comment-terminator searches can also rescan the remaining suffix for each comment. These are source-derived growth risks. The local timing does not establish them as current bottlenecks. [HTML tokenizer](../../tools/build-prod-projection.mjs)

### Data structures at the materializer boundary

Keep the declared JSON as the editing surface. Its records carry a semantic token, exact URL, allowed carriers and selection rationale. The materializer already indexes tokens with a Map and detects duplicate destinations with a Set. The profitable new indexes are the **reverse joins** described above. Use private per-plan indexes so a source revision or a different publication selection cannot inherit an earlier plan’s authority. [External bindings implementation](../../tools/external-reference-contract.mjs)

`URLSearchParams` fits **query parameters of one URL**. The materializer already reads `url.searchParams.keys()` during URL admission. For a future UI that intentionally constructs a query such as `?section=qc`, it would also be appropriate at the point of construction. Preserve the reviewed URL string when emitting a binding. Parameter lists admit duplicate names, and reserialization can turn `%20` into `+` or encode `~`. A fragment has its own semantics. A token lookup needs neither query serialization nor this ordering behavior. [Materializer URL admission](../../tools/materialize-public-references.mjs) · [WHATWG URL standard](https://url.spec.whatwg.org/#interface-urlsearchparams) · [Node URL API](https://nodejs.org/api/url.html#urlsearchparams)

GraphQL field selection would help a future network consumer asking for a small, variable view of a large publication graph. This builder already has an explicit manifest and must verify the entire selected closure, including byte lengths and hashes. A Yoga server would add schema, resolver and runtime ownership while those reads remained necessary. If a metadata-only explorer becomes a real consumer, expose the existing plan through a read-only in-process selector first. Consider GraphQL when several clients actually need different field sets. Resolver batching and per-request cache scope would still matter. [GraphQL selection sets](https://graphql.org/learn/queries/#fields) · [DataLoader’s batching and cache scope](https://github.com/graphql/dataloader#caching-per-request)

## One sequence of work

1. **Give developers the shortest credible answer.** Use the existing suite planner to name the affected family and the existing npm entry point. Keep the full three-engine run selectable for changes spanning shared browser behavior or release acceptance. Report queue, install, suite execution and total runner-minutes separately.
2. **Pilot browser prerequisites alone.** On the next authorized preparation exercise, compare a cold install and a trusted cache restore with the same lock, image and engine selection. Check launch/close and relevant font/media support. Use the next already-needed full run to confirm equivalent case membership. A two-minute setup target would put the observed 33m20s job near 25m32s with execution held constant. Restore the ordinary 30-minute ceiling once comparable observations show operating margin, including the cold recovery path. Use a pinned image only if the package pilot falls short.
3. **Recover execution time without dropping evidence.** Time the CSS proof’s render, property capture and digest phases on one representative scenario. Remove the redundant style capture from the structure-only mutation. Examine the slow Core reference scenarios next. Check old/new records, case IDs and recovery behavior on focused fixtures. Consider two groups only if full-run latency still misses the agreed target and the additional runner-minutes are acceptable.
4. **Deliver the build improvement independently.** Put a length-framed Git batch reader behind the two existing blob-reading boundaries. Validate requested ID, reported ID/type/length, configured limits, binary payload length and terminator. Close the process on partial input or error. Keep checked path/mode and final source revalidation with their current owners. Compare outputs, TSV, receipt digests and archive bytes at a fixed source, profile, toolchain and receipt timestamp. Recheck missing objects and malformed replies.
5. **Remove the verified quadratic joins, then stop and measure.** Start with the two carrier membership scans, then the binding-owner and iframe-pair joins as their populations warrant. Confirm duplicate, missing, extra and ambiguous cases still produce useful failures. Revisit streaming, cross-run artifact caches or sharding only when another measured constraint justifies their maintenance.

This spike used existing Actions logs, source inspection, a local scratch projection and a Git read comparison. Browser check execution, workflow dispatch, release staging and deployment were outside the measurement.
