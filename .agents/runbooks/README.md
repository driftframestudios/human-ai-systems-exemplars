# AI collaboration runbooks

Runbooks sequence existing owners through a known, multi-phase repository job.
They let a cold or returning collaborator identify the entry condition, act
within granted authority, verify the changed boundary, recover from a named
failure, and hand the work back without reconstructing the procedure.

## Choose the right instruction form

| Work shape | Use | Authority and return |
| --- | --- | --- |
| Known multi-phase procedure | A runbook in this directory | The runbook orders existing owners and ends with a handback. |
| One finite contribution | A [bounded support request](../skills/bounded-support-routing/README.md) | The request names one action mode, observable return, and stopping event. |
| Branching diagnosis or exploration | A playbook owned by the relevant system | Each branch keeps its own evidence and recovery condition. |
| Current outcome and acceptance | A GitHub Issue | The Issue remains the collaboration docket and current decision boundary. |

Tracked runbooks in this directory are written for public release. Internal-only
procedures stay with their authorized private workspace and link outward to a
public explanation when one exists. Each runbook header carries its exact
version, maturity, audience, source band, and task type; Git carries chronology,
while the current Issue carries the active work decision.

## How to execute and return

1. Read the selected runbook completely and identify its entry, authority, stop, and re-entry conditions.
2. Confirm current source, Git, GitHub, environment, and account state through the owners named by the runbook.
3. Execute one phase at a time and stop at each human-held or access-controlled boundary.
4. Run the smallest check that establishes the phase's changed claim.
5. Preserve accepted coordinates and recovery state before advancing.
6. Return the changed state, what the evidence establishes, its coverage boundary, and the exact next receiver.

The runbook orders the procedure. Runnable source owns behavior, manifests and
release records own their declared coordinates, GitHub owns current work state,
and named people retain identity, publication, transfer, credential, and other
human-held decisions.

For the bounded job of preparing a shell-free cPanel carrier, begin with the
[deployment quick entry](../../deployment/cpanel/README.md#quick-entry-prepare-a-shell-free-cpanel-carrier).
It distinguishes packaging an existing annotated tag from building a new
source/carrier release and routes the transfer and recovery details to their
canonical guide.

The [`collaboration-runbook-authoring` overview](../skills/collaboration-runbook-authoring/README.md)
and [authoritative contract](../skills/collaboration-runbook-authoring/SKILL.md)
own the portable authoring method. A runbook is complete when it and
its linked current owners give another collaborator enough orientation to
enter, act within granted authority, verify, recover, and return. A repeated
concrete drift case can earn a validator or additional metadata later; this first
practice remains instruction-only.
