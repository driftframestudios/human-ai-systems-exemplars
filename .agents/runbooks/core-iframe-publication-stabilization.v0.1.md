# Iframe and production publication stabilization

## Desired receiving state

The accepted visitor and prototype sources produce one deterministic aggregate
iframe package beneath `/v1/`, with Core and Canvas retained as distinct route
families. That exact package and the accepted primary-site source feed two
disjoint, deterministic cPanel closures. Human-reviewed promotion and cPanel
deployment place both closures; signed-out observation then establishes the
direct hosted responses and every manifest-covered parent-carrier
relationship. The same accepted source coordinate feeds the smallest public
route documentation and the human-selected long-lived branch receivers.

Issue
[#464](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/464)
owns the current source, carrier, tag, activation, and live-acceptance cycle.
Closed Issues in the source-contract table preserve implemented decisions and
historical receipts; they supply precedent while #464 carries the current
release coordinate. #72 and #102 continue to own iframe activation and
parent-carrier response observations, and #406 owns current schema delivery.

Completion is one accepted `main` coordinate whose source, exact aggregate iframe
package, primary and iframe cPanel closures, reviewed promotion, observed-live
routes, parent carriers, documentation standing, and next branch receiver are
distinguishable. Each owning Issue keeps its own acceptance decision.

## Entry condition

Begin implementation in a clean task worktree; first inspect and preserve the
shared worktree. Read
[`AGENTS.md`](../../AGENTS.md), the nearest README for the assigned phase, and
the active Issue before selecting an action mode.

```sh
git status --short --branch
git rev-parse HEAD
git log -5 --oneline --decorate HEAD
```

When the current task permits a networked repository read, refresh and inspect
the remote coordinate:

```sh
git fetch origin
git rev-parse origin/main
```

Preserve an existing dirty worktree and unrelated changes. Use a separately
authorized clean worktree for implementation, or return `friction`; do not
clean, reset, or switch over work whose ownership is not established. If
`git fetch` is unavailable, label local remote refs unverified and do not call
them current. If a required loopback or browser check cannot run in the local
environment, route that exact observation through the approved bounded-support
or CI browser worker while retaining the check's evidence boundary.

The current task grant supplies mutation and external-action authority. The
active Issue supplies scope, owners, and acceptance; tool and repository
policy bound operations. This runbook and an open Issue provide orientation.
When the task grants no mutation, use
`observation_only`: reconstruct current truth, return the smallest next
packet, and leave repository and external state as found.

## Conditional preparation

Use Node 22 or newer. Install the locked root dependencies with
`npm ci --ignore-scripts` when they are absent and the current task permits
dependency installation. Install the focused Chromium runtime with
`npm run playwright:install` when a named browser check requires it. Prepare
the Betterleaks helper with `npm run security:secrets:install` only when the
named secret-boundary check requires it and the helper is unavailable.

When local dependency download or browser launch is unavailable, route the
exact check through the approved bounded-support or CI browser worker. Retain
the same command, viewport or route coverage, evidence claim, and safe return.

Before cPanel activation, select one human-authorized, host-supported receiver.
A shell-capable account can use the managed-clone and Bash-installer route. A
shell-free account can use a verified carrier archive, private staging, and a
human-operated cutover through the repository-owned transfer-envelope builder
and verifier. Keep credentials, exact account paths, and host limits with the
protected receiver. When neither route has a verified staging and recovery
path, stop at the reviewed cPanel closures and return `friction`; the repository
remains private and the deployment phase remains at rest.

### Phase 4 — Review, promote, and deploy both cPanel closures

**Action mode:** `implementation_authorized` only when the current task grants
the named promotion or protected cPanel action. Human review retains the
release, destination, credential, and recovery decisions.

Review the exact source SHA, aggregate package coordinate, both closure
manifests, secret-boundary result, and recovery path. Follow the canonical
[accepted release sequence](../../deployment/cpanel/README.md#accepted-release-sequence)
from source promotion through the carrier-only release. The host capability
then selects one receiver:

- a shell-capable account follows the [pull-model enrollment and cutover
  guide](../../deployment/cpanel/FIRST-CUTOVER.md) for managed-clone
  registration, private configuration, backup, canary rehearsal, cPanel's
  **Update from Remote** and **Deploy HEAD Commit** actions, and recovery; or
- a shell-free account follows [artifact delivery and first
  cutover](../../deployment/cpanel/SHELL-FREE-ARTIFACT-DELIVERY.md) for an
  immutable archive, private File Manager staging, backup, ordered two-root
  convergence, recovery, and later bounded automation.

When a protected destination requires the pull-request head to contain its
current base, form a short-lived destination-based promotion candidate rather
than merging downstream history into the canonical upstream branch. Record:

- `U`, the exact accepted upstream coordinate;
- `D`, the exact current destination coordinate;
- `C`, the temporary candidate created at `D` and merged with exact `U`; and
- `P`, the reviewed promotion result. For `release → prod`, `S = P`; `R`
  remains reserved for the subsequent carrier-only merge result.

Before publication, verify `C^1 = D`, `C^2 = U`, and both ancestry relations.
For `stg → release`, the candidate and accepted result trees equal the accepted
staging tree. Merge the reviewed candidate with a merge commit and verify
`P^1 = D` and `P^2 = C`; squash, rebase, and fast-forward results do not carry
the required topology receipt. For `release → prod`, every path outside
`deployment/cpanel/carrier/**` equals the accepted release, while the complete
carrier subtree—including path set, modes, and bytes—equals the prior production
destination. Verify both relationships on `C` and accepted production source
`S = P`. The retained carrier is historical downstream state until the
following carrier-only branch replaces it from exact `S`.

Use the full recorded SHAs in an isolated worktree. This equivalent command
sequence supplies the first deterministic verification surface while #469 owns
the focused checker and material failure-path tests:

```sh
test "$(git rev-parse "${C}^1")" = "$D"
test "$(git rev-parse "${C}^2")" = "$U"
git merge-base --is-ancestor "$D" "$C"
git merge-base --is-ancestor "$U" "$C"
git diff --exit-code "$U" "$C" -- . ':(exclude)deployment/cpanel/carrier/**'
test "$(git rev-parse "${D}:deployment/cpanel/carrier")" = \
  "$(git rev-parse "${C}:deployment/cpanel/carrier")"
```

After the reviewed merge, apply the same checks with `S` in place of `C`, then
also require `S^1 = D` and `S^2 = C`. For a destination without an intentionally
retained carrier closure, require complete tree equality with `U` instead.

Push only the temporary candidate, run the destination checks, and receive
human approval after its final commit. A destination move forms a fresh
candidate from the new exact `D`; a conflict or unexpected path delta returns
to the source-owning lane. After merge, record `P` and its parents, verify the
same source and carrier relationships, then retire the temporary ref once the
durable receipt exists. This procedure prevents future repetitions of PR
#468's downstream-history merge into canonical `stg`; it preserves that
accepted history without rewrite. [#469](https://github.com/driftframestudios/human-ai-systems-exemplars/issues/469)
owns refinement of this procedure.

#464 owns the current branch promotion, activation, and shell-free release;
#108, #118, and #253 preserve the accepted topology, projection, and adapter
precedents. The accepted source, production tag, manifest,
and file index select publication membership before either host receiver
accepts the release.

release mechanism. The shell-capable route adds its bounded deploy credential;

A separately granted iframe-only manual upload remains an interim compatibility

**Checkpoint:** The reviewed promotion and host task establish that the
accepted prebuilt closures were selected for both document roots. The pull

**Recovery and stop:** An unconfirmed host receiver, unknown document root,

## Neighboring Codex bounded lane

## Public-safe handback

Use one receiving surface:

```text
Disposition: pass | friction | blocker
Accepted source: exact public revision; branch only as context
Package and closure coordinate: public manifests and digests when produced
Changed public surfaces: concise paths or pull request
Validation: normalized command and result
Establishes: the affirmative evidence state
Coverage boundary: the adjacent claim still open
Next receiver: Issue and re-entry event
```

Sensitive browser responses, raw logs, headers, credentials, signed URLs,
private workspace locators, account paths, protected destinations, and
user-specific filesystem paths remain with their existing access-controlled
receiver. The public handback names the bounded condition and next owner.

## Release and re-entry

The runbook releases when both cPanel closures from one accepted coordinate are
deployed; the primary site, direct iframe routes, and every selected parent
carrier have their accepted observations; #464 accepts the settlement; and
every remaining long-lived branch has its own reviewed advance or explicit
rest. A source, package, asset-inventory, route, response-policy,
production-projection, host-access, or branch-topology change reopens the
matching phase through its owning Issue; the remaining phases stay at rest
until their entry condition forms. A change in the external `gist-registry`
alone leaves this runbook at rest; a #128 input accepted into this repository
re-enters at Phase 1.
