# Repository handoff readiness

Prepare a repository that another owner can continue through plain-language
Issues with an authorized AI collaborator. This skill keeps source behavior,
account decisions retained by their human owners, the live work route, and the
receiving owner's next action visible throughout the handoff.

## Start here

- [Read the authoritative skill contract](SKILL.md)
- [Return to the repository skills catalog](../README.md)

## Use it when

Use this skill for a repository transfer, template-based creation, fresh
installation, or source intake that should lead to continuing ownership. An
ordinary bounded change in a repository with a current owner can use the
repository collaboration cycle instead.

## What it returns

- an explicit delivery form and source standing;
- the smallest fitting capability profiles;
- one live Issue currently receiving the work;
- a source, settings, and evidence receipt with held decisions; and
- one `next_owner_action` plus an observable re-entry event.

## Concrete example

| Part | Example |
| --- | --- |
| Situation | A site repository will transfer to a colleague before its first private release, and incoming source has already established the framework and package manager. |
| Use | Compare the live repository with the required capability profiles, preserve its source and lockfile, prepare a current Issue, and keep credentials and transfer acceptance with their human owners. |
| Observable return | The receiving owner enters through one current Issue, can run the source-native checks, sees every held account decision, and completes one ordinary Issue-to-change cycle. |

## Capability profiles

Select only what the observed source and receiving use require:

1. **Foundation:** orientation, Issue route, concept intake, and a small validator.
2. **Received site:** source receipt, technology profile, reproducible preview, and visual contract.
3. **Stable private release:** fitting tests, privacy review, release identity, and recovery coordinate.
4. **GitHub Pages:** source-native artifact and an owner-activated deployment route.
5. **Service-backed extension:** server, data, authentication, secret, or cross-repository delivery.

## Working route

1. Reconstruct current source, GitHub, planning, and owner truth.
2. Name what the receiving owner should be able to do and which decisions remain human-held.
3. Classify each proposed addition as materialize, bind, preserve existing, or hold.
4. Make the current Issue and its next receiver legible.
5. Let received source select application dependencies and checks.
6. Prepare the smallest fitting foundation and handoff evidence.
7. Observe one continuing collaboration cycle and return any reusable friction.
