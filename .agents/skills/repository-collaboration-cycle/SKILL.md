# Repository collaboration cycle

## Contract

- **What:** A source-grounded route from repository entry to one receiver-ready result and a precise continuation point.
- **When:** A named repository task needs current-state recovery, action classification, issue-specific execution, fitting evidence, and a handback.
- **Boundaries:** `repository-reentry` owns truth reconstruction; the active Issue owns scope and acceptance; domain skills and runnable source own material behavior; the current task grants repository mutation and external actions. Merge, publication, deployment, and destructive operations begin through their explicit grants. Optional support augments the primary collaborator through its own finite packet.
- **Result:** One live branch, pull request, decision-ready finding, or legibly held route carries a one-sentence scope, concrete changes, exact validation and result, environment-behavior note, next receiver, and exact re-entry action.

## Fit and attention

- **Useful when:** Orientation and execution belong to one continuous repository cycle, especially for a cold or resumed collaborator expected to deliver more than a status map.
- **Poor fit when:** `repository-reentry` alone supplies the complete result, one finite support packet owns the job, an exploratory playbook still needs to discover the route, or `collaboration-runbook-authoring` is itself the only requested result.
- **Interactions:** `repository-reentry` establishes current ground; the selected runbook supplies repository-specific phases; domain skills own material work; `bounded-support-routing` owns an optional finite contribution; `supportive-change-writing` shapes the handback; `collaboration-accounting` receives contract-changing observations.
- **Rest or release when:** A receiver-ready handback is placed with its next receiver and exact action, or a held route names its release signal and responsible receiver.

## Rules

### Rule: Current truth supplies the action coordinate

The cycle begins with the branch, revision, worktree, nearest instructions, runnable source, active Issue or pull request, and relevant planning and threadkeeping state. Cached remote state is labeled as cached; a network-authorized read establishes current remote state.

### Rule: One primary route owns synthesis

Each candidate enters one route: direct action, primary collaboration with bounded support, or a held route awaiting a named authority, environment, dependency, or evidence signal. The primary collaborator integrates every return and owns the final evidence statement.

### Rule: Environment preparation follows the evidence question

Inspect the lockfile, scripts, installed dependencies, browser runtime, and existing local tools first. Install locked dependencies when the selected check requires them and the task permits installation. Install a named browser runtime when rendered evidence is part of acceptance. Record environment changes that could affect behavior, disk use, or reproducibility.

### Rule: Dependency repairs preserve two evidence claims

Dependency findings group by the direct dependency or lockfile edge that can repair them. The selected release follows the repository's engine and pinning contract; current maintainer advisories establish affected and fixed versions. A regenerated lockfile and clean install establish reproducibility. The audit establishes the known-advisory state, while focused consumer checks establish behavior after the upgrade. Browser bundles, local development services, build tools, and hosted code retain their distinct exposure boundaries. A clear audit leaves unobserved runtime and security claims open for their fitting evidence.

### Rule: Support capacity is a conditional receiver state

Available capacity can receive one bounded packet with an action mode, observable return, and stop condition. While capacity rests, the primary route remains active. A still-useful packet can rest as `awaiting_capacity` on the active Issue or named access-controlled task; activation refreshes the source revision, Issue acceptance boundary, and continuing need before action.

### Rule: Evidence states what it establishes

Each validation signal leads with its established state, then names its coverage boundary. The adjacent claim remains open until the fitting observation or receiver establishes it.

### Rule: Delivery preserves the next useful move

The handback names changed surfaces, purpose, exact command and normalized result, environment behavior, current Issue or pull request, next receiver, and one exact re-entry action. One receiving surface carries the durable return.

## Operating sequence

1. **Re-enter:** Use `repository-reentry` to reconstruct current source, Git, GitHub, planning, threadkeeping, and behavior truth.
2. **Classify:** Select direct action, primary work with optional bounded support, or a held route with one observable release event.
3. **Prepare:** Inspect the environment and prepare only the dependency, browser, scanner, or generated-artifact lane selected by acceptance.
4. **Bind:** Create or restore the issue-specific branch and preserve unrelated work at its existing coordinate.
5. **Execute:** Apply direct reasoning or the fitting domain skill. Keep one primary collaborator responsible for integration and scope.
6. **Integrate support:** When a bounded return exists, verify its premise, revision, diff, and evidence before adopting it.
7. **Verify:** Run the smallest source-owned checks that answer the receiving question and state their affirmative evidence boundary.
8. **Deliver:** Place the reviewable change, decision, or held route on one named surface with the required handback fields.
9. **Re-enter exactly:** Record the source coordinate, next receiver, and one action that resumes the work directly.

## Completion

The cycle completes when one receiver can inspect the result and its evidence on a named surface, repository state remains legible, and the next collaborator can resume from an exact source coordinate and action. A fresh-context use can revise the working contract when it exposes a decision-changing gap; otherwise the skill rests after handback.
