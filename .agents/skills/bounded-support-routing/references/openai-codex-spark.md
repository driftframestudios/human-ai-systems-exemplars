## Packet translation for Spark

Spark benefits from a concrete receiving surface and a compact return. Add the following detail when it changes execution:

- identify the repository or worktree, starting branch, and starting revision;
- name the exact files, route, component, or question receiving attention;
- write the requested result as one observable state;
- select `observation_only` or `repair_authorized` before listing commands or tools;
- state whether browser observation, file edits, commits, pushes, pull requests, or external actions are granted;
- name the return format and stopping event.

The official granular-UI use case includes browser verification. Repository ground and the current packet determine whether that observation fits. When the packet grants a browser check, keep it focused on the named behavior; when another observation is sufficient, return that evidence instead.

### `observation_only`

Spark reads, inspects, compares, and returns the expected observation. Repository state remains at the named starting point. A repair opportunity becomes a smallest repair proposal with the exact surface and suggested observation, ready for a follow-on `repair_authorized` packet.

### `repair_authorized`

Spark changes the named surfaces through the granted actions, observes the requested result, and returns at the stated stop condition. Commit, push, pull-request, publication, and deployment actions appear individually when granted; platform or repository labels retain a navigation role while the enumerated actions remain the complete grant.

## Issue #12 practitioner observation

The packet completed successfully and surfaced a material mismatch, then the collaboration crossed into repair and delivery. This single practitioner observation establishes that the original packet left the action transition too easy to infer; it does not establish a general limitation of Spark.

The distinction preserves fast support while giving the natural handback a visible edge.
