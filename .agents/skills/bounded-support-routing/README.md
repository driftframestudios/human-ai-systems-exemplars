# Bounded support routing

Use this skill to give one finite contribution a clear result, action boundary, observable stop, and handback. The packet lets a receiver understand the work without inheriting an open-ended undertaking.

## Start here

- Read the authoritative [skill contract](SKILL.md).
- Choose one route: `Solution`, `Implementation`, or `Recovery`.
- Choose one action mode before tool use: `observation_only`, `repair_authorized`, `implementation_authorized`, or `recovery_authorized`.
- Name the opportunity, focal artifact or behavior, requested result, granted actions, held boundaries, expected observation, recovery route, handback, and stop condition.

## Concrete example

**Situation:** A reviewer wants to know why a figure caption crosses its painted background at one viewport. The current grant covers inspection and a recommendation, while the page source stays unchanged.

**Use:** Form an `observation_only` packet focused on the figure and its CSS owner. Grant source reading and a focused browser check. Define the stop condition as a reproducible geometry finding or evidence that the reported condition is absent.

**Observable return:** One handback names the observed width, owning selector, normalized result, what the check establishes, and the smallest repair route. Repository state remains at its known-good coordinate until a `repair_authorized` packet grants the change.

## Boundaries

A skill name, route label, or Issue label provides orientation rather than authority. The explicit grant governs reads, mutation, publication, merge, deployment, and external actions. Once a stop condition forms, remaining state-changing actions pause and the evidence handback continues.
