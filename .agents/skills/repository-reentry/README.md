# Repository re-entry

Reconstruct the repository state that matters before resumed work begins. This
skill distinguishes current behavior, settled rationale, open collaboration,
and the next bounded action using inspected current state in place of presumed memory.

## Start here

- [Read the authoritative skill contract](SKILL.md)
- [Return to the repository skills catalog](../README.md)

## Use it when

Use this skill after a pause or handoff, or when source, branches, Issues,
pull requests, planning notes, and threadkeeping records appear to disagree.

## What it returns

- one named source path for current behavior;
- one live collaboration record when current ownership matters;
- a concise account of settled, current, open, and next terrain; and
- a visible stale-record or evidence boundary when sources differ.

## Concrete example

| Part | Example |
| --- | --- |
| Situation | A threadkeeping note describes an earlier behavior, while the accepted feature branch and its pull request contain a later implementation. |
| Use | Inspect Git state, the nearest README, the focused plan and ledger, the pull request, and the runnable source. |
| Observable return | The accepted branch is named as behavior authority, the historical note retains its rationale role, and one next action tells the collaborator where to resume. |

## Working route

1. Inspect the worktree and recent local and remote history.
2. Read the nearest README for standing orientation.
3. Read only the planning and threadkeeping records that affect the task.
4. Inspect the relevant Issue or pull request when live state matters.
5. Let runnable source or an artifact resolve remaining behavior questions.
6. Return the smallest current model and one bounded continuation.

Existing worktree changes retain their ownership throughout this route.
