# Source authority mapping

Show which source defines meaning, where a current representation can be
retrieved, who can publish or accept it, and how a later collaborator returns
to the lineage. This skill keeps ownership legible when material travels among
repositories, workspaces, snapshots, mirrors, and public pages.

## Use it when

Use this skill when semantic ownership, authored source, schema authority,
publication authority, delivery operation, or receiving ownership could be
mistaken for one another.

## What it returns

- the material object and decision in view;
- independently named authority roles;
- typed relations such as `projects`, `snapshots`, `mirrors`, or `consumes`;
- the receiving and promotion boundary; and
- an exact re-entry condition.

## Concrete example

| Part | Example |
| --- | --- |
| Situation | A visitor-facing page cites a private working page while a reviewed public Registry page now carries the same construct. |
| Use | Confirm definition equivalence and publication standing, point the visitor to the public receiver, and preserve the private source in the authorized lineage record. |
| Observable return | Visitors receive a usable public route, uncovered claims remain visible for adaptation, and the authorized resolver retains the exact locator for future source-lineage recovery. |

## Working route

1. Name the claim, artifact, contract, schema, or package whose route affects a decision.
2. Locate its semantic source and record the relevant publication boundary.
3. Trace only the projections, snapshots, mirrors, handoffs, and consumers that matter.
4. Separate identity, retrieval, publication, delivery, and receiving roles.
5. Choose the smallest link, adaptation, snapshot, promotion, deferral, or steward question.
6. Preserve a source pointer, accepted coordinate, relation, evidence limit, and re-entry condition.

The map ends at the receiving decision and includes the platforms relevant to
that decision.
