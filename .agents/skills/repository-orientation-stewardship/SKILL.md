# Repository orientation stewardship

## Contract

- **What:** A source-aware pass that makes one repository's README graph useful at first receipt and trustworthy on return.
- **When:** A root README, family catalog, nested README, snapshot boundary, or machine companion needs coordinated orientation rather than a local wording edit.
- **Boundaries:** Runnable source, manifests, release records, GitHub, and named human decisions retain their authority. Versioned or accepted artifact bytes stay stable unless their owner authorizes a successor. A README routes to current truth; it does not become a second status ledger or an AI-only source of truth.
- **Result:** A reader can identify the repository's purpose, current state, quickest useful proof, evidence boundary, source owners, and next route without inferring missing relationships.

## Fit and attention

- **Useful when:** several README routes serve different encounters, current-state prose has drifted from its owners, or a cold reader must traverse exhaustive detail before finding practical value.
- **Poor fit when:** one accurate sentence or one broken link needs a local repair; direct editing plus the nearest check is sufficient.
- **Smallest useful dose:** repair the current-truth statement and add one intent-based route to its existing owner.
- **Foregrounds:** first receipt, repeat use, re-entry, typed source relations, and what a check establishes.
- **May under-attend:** the full depth of domain material, which stays with its owning source and subject-matter review.
- **Interactions:** `repository-reentry` establishes current truth; `source-authority-mapping` resolves ownership; `supportive-change-writing` shapes prose; `contextual-jargon-scan` tests inside language; `secret-boundary-inspection` governs publication-facing material when that boundary enters scope.
- **Rest or release when:** the README graph answers the active reader jobs, current state points to its owners, and another layer would only restate existing routes.

## Rules

### Rule: One truth can support several encounters

The root serves first receipt, family and owner READMEs support repeat use, and live work plus machine records support re-entry. Each layer summarizes the same owners at the depth its reader needs.

### Rule: Practical value precedes repository exhaustiveness

The first screen answers what this repository enables, what is current, which route fits the reader's intent, and what can be inspected or run now. Full inventories remain available through descriptive links and repository maps.

### Rule: Mutable state stays one derivation edge from its owner

A README labels each state axis and links to the record that owns it. It avoids manually duplicating hashes, run identifiers, release observations, or current-work claims when a manifest, receipt, GitHub surface, or generated projection already carries them.

### Rule: Nested READMEs complete a round trip

Each maintained nested README names its reader job, source owner, fitting verification, evidence boundary, next route, and return path. A placeholder names its current standing and available material rather than borrowing content from an unavailable source.

### Rule: Snapshots announce their standing before their content

An integrated copy, mirror, or accepted exact version identifies its living source and capture boundary before a reader treats its README as current collaboration truth. Orientation overlays live outside immutable bytes unless the snapshot contract explicitly includes their regeneration.

### Rule: Human and machine routes share semantic labels

Stable ordinary headings such as `Purpose`, `Current state`, `Choose your route`, `Quickest proof`, `Evidence and authority`, and `Repository map` support human scanning and machine retrieval. Machine companions add typed state; they do not justify a parallel prose authority.

### Rule: Validation protects the route actually changed

One repaired link needs a link observation. A generated catalog or repeated drift can earn a focused contract that checks registered membership, local paths, headings, or selected status agreement. Passing evidence names the route it exercised and leaves semantic quality and acceptance with their fitting reviewers.

## Operating sequence

1. **Re-enter:** Confirm branch, worktree, live Issue or pull request, nearest instructions, and the current README graph.
2. **Name readers and encounters:** Identify the first-receipt, repeat-use, re-entry, evaluator, adopter, maintainer, and release-auditor jobs that materially exist.
3. **Map authority:** Connect every mutable claim to its runnable source, manifest, release record, GitHub receiver, or named human decision.
4. **Find route strain:** Locate stale state, missing registered families, ambiguous snapshots, exhaustive first screens, placeholder routes, and nested pages without a return path.
5. **Select the smallest architecture:** Keep one layered root, add or repair family catalogs and owner READMEs, and preserve exact-version artifacts.
6. **Write toward use:** Lead with practical value and current state, use intent-based links, state what each proof establishes, and keep boundaries beside their affirmative replacement route.
7. **Verify:** Exercise local links and fragments, registered route coverage, authoritative status fields, and any repository-specific documentation checks.
8. **Return:** Name changed surfaces, evidence, coverage boundary, review receiver, and the exact re-entry action.

## Representative scenarios

### Scenario: A release repository has a newer integration branch

- Given the default branch is the accepted release line and a development branch contains later collaboration assets
- When its root README is revised
- Then the first screen names both roles without presenting integration work as released behavior
- And each current-state claim links to the record that owns it

### Scenario: An integrated snapshot contains standalone READMEs

- Given captured member directories preserve exact source revisions
- When the integrated collection needs clearer orientation
- Then the parent route identifies the living repositories, capture coordinates, and snapshot standing before linking inward
- And scan aids live in the parent or an authorized generated overlay while captured bytes remain intact

## Completion

The pass completes when the active reader jobs can reach practical value, current truth, authority, evidence, and a return path in one coherent traversal; focused checks cover the changed route; and review remains with the repository's named receiver. A state change, missing route, reader failure, or materially different repository family can reopen the contract.
