# CI provisioning and runner efficiency

Load this reference when environment preparation or dependency transfer
materially affects feedback time, reliability, or Actions budget. The route
optimizes the setup owner while preserving the complete behavior proof selected
by the suite composition.

## Begin with a phase receipt

Measure a comparable cohort at an exact source coordinate and record:

| Phase | Examples | Decision it can support |
| --- | --- | --- |
| Queue and runner start | scheduling, image allocation | runner availability or concurrency |
| Repository and runtime preparation | checkout, runtime admission, locked install | source and toolchain setup |
| Dependency provisioning | browser, package manager, system libraries | hosted tool, cache, or image choice |
| Behavior execution | unit, integration, browser, visual | suite topology and segmentation |
| Artifact compilation | bundles, Workers, packages | build ownership and reuse |
| Publication or delivery | upload, deploy, live probe | receiver and authorization topology |
| Cleanup and summary | teardown, receipts | interruption and diagnostic quality |

Report individual observations. Add median, range, percentile, or variance only
after the cohort has a comparable source, population, runner, and phase method.

## Provisioning choice ladder

Choose the first route that satisfies the version, integrity, evidence, and
recovery contract.

1. **Reviewed runner capability.** Use an already available browser or tool when its coordinate satisfies the narrow receiving check. Keep independently pinned cross-engine or compatibility coverage in its existing owner.
2. **Verified dependency cache.** Restore package archives or immutable tool bytes under a semantic identity. Let the package manager or artifact verifier retain signature, hash, candidate-version, and admission authority.
3. **Prebuilt runner or container.** Pin the base and consumer image by digest, bind every material runtime and browser coordinate, publish SBOM and provenance, measure pull time, and keep rebuild and rollback procedures.
4. **Larger or self-hosted runner.** Adopt when measured queue, compute, network, or device needs justify the patching, access, capacity, and billing ownership.

Parallel jobs may reduce elapsed time while increasing total billed work. Add
them when the receiving time objective and budget accept that tradeoff.

## Cache identity and authority

A useful key describes semantic compatibility rather than a branch name alone.
Include the dimensions that can change the admitted bytes:

- cache schema version;
- operating system and architecture;
- runner or container image coordinate when system ABI matters;
- package-manager or runtime coordinate when resolution semantics matter; and
- a digest of the resolved dependency plan or immutable lock closure.

An authored package list may resolve to different transitive versions over
time. Hash the resolved plan when the package ecosystem supports that route.
Use a broader restore prefix only across dimensions whose compatibility has a
named verifier.

Separate restore and publication authority:

- pull requests and untrusted contributions may restore an accessible closure;
- a trusted branch or release receiver publishes a new closure after every
  required behavior and compilation proof succeeds; and
- cache-service failure follows the direct preparation route and records the
  resulting standing.

Store dependency archives or another deliberately bounded closure. Keep
credentials, browser profiles, logs, generated receipts, mutable working
trees, and unrelated installed directories with their existing owners.

## Required standings

Name every route the receiver must interpret:

| Standing | Meaning | Continued proof |
| --- | --- | --- |
| Exact hit | Full semantic key matched | Verify dependencies and run every selected behavior check |
| Compatible restore | Reviewed prefix matched | Verify compatibility and run every selected behavior check |
| Rejected restore | Exact or compatible bytes restored and the verifier rejected identity, integrity, or compatibility | Preserve the rejection signal, prepare directly, run every selected behavior check, and route key invalidation or versioning to the cache owner |
| Miss | Reusable bytes were absent | Prepare directly, run every selected behavior check, and publish only through the trusted receiver |
| Unavailable | Cache service or restore mechanism failed | Prepare directly and record the degraded path |
| Cancelled | Execution stopped before completion | Preserve prior accepted evidence and partial cleanup standing |
| Skipped | Policy or trigger kept the lane at rest | Name the policy and the claim left for its receiver |

A verified hit can change preparation cost. The cache service establishes key
match and restoration. The package verifier establishes admitted dependency
bytes. The behavior suite establishes application behavior. A live receiver
establishes delivery. Keep these evidence meanings distinct.

## Decomposition decision

Define a lane ceiling with its budget owner. Measure which phase approaches it:

- provisioning pressure routes to hosted capability, verified cache, or a
  prebuilt toolchain;
- test-execution pressure routes to family, state, or engine segmentation;
- compilation pressure routes to build-graph and artifact reuse; and
- publication pressure routes to receiver topology and transfer design.

For the Human–AI Systems Exemplars browser receivers, thirty minutes is the
current decomposition trigger. This repository owns that adapter. Each other
repository selects its own ceiling from feedback needs, budget, runner policy,
and release consequence.

## Receipt fields

Return the smallest table that another collaborator can compare:

- source revision and workflow or job identity;
- runner image, operating system, architecture, runtime, browser, and tool versions;
- resolved-plan or lock digest;
- exact, compatible, rejected, miss, unavailable, cancelled, or skipped standing;
- preparation, test, compilation, publication, and total elapsed time;
- selected and executed population, including skips or reuse;
- behavior and compilation outcome;
- fallback or rollback coordinate; and
- the next receiver for warm observation, release acceptance, or decomposition.

An exact-head cold run establishes cold behavior and duration. Warm-cache
performance receives its own exact-head observations after a trusted receiver
publishes the closure.

## Recovery

Keep a direct preparation path that uses the same reviewed dependency manifest
and verifier. A focused rollback removes restore and publication steps while
retaining behavior checks. A prebuilt image keeps its previous digest until the
replacement image and rollback receive review. When timing remains variable,
preserve the individual observations and investigate the phase that owns the
variation before changing suite population.
